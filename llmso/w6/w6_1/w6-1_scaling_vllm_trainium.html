Init Container
메인 서버 컨테이너보다 먼저 실행되어 준비 작업(모델 다운로드·컴파일·캐시 업로드)을 마치는 컨테이너.
S3 Mountpoint (FUSE)
S3 API를 파일시스템처럼 보이게 하는 유저스페이스 파일시스템. 커널 블록 디바이스가 아니다.
KV 캐시
이전 토큰 계산 결과를 저장해 다음 토큰 생성 때 재사용하는 메모리.
성능 지표
TTFT (Time To First Token)
요청 전송부터 첫 토큰 생성까지 걸리는 시간. Prefill 효율성을 반영.
ITL (Inter-Token Latency)
연속 출력 토큰 사이의 생성 간격. Decode 효율성과 스트리밍 체감 속도를 반영.
TPS (Tokens Per Second)
초당 처리 토큰 수. 요청 1개 기준(request throughput)과 전체 동시 요청 합산(overall throughput)을 구분해야 한다.
오토스케일링
HPA (Horizontal Pod Autoscaler)
메트릭 기준으로 Pod 개수를 자동 조절하는 Kubernetes 리소스.
KEDA / External Scaler
KEDA는 외부 메트릭을 HPA에 연결해주는 오토스케일러. External Scaler는 gRPC 인터페이스(IsActive/GetMetrics 등)로 커스텀 메트릭 소스를 붙이는 방식.
NVML
NVIDIA GPU 상태를 읽는 라이브러리. AWS Neuron/Trainium 메트릭은 읽을 수 없다.

AWS Neuron 소개

AWS Neuron은 AWS가 설계한 ML 가속기(Inferentia, Trainium)를 위한 SDK/소프트웨어 스택입니다. 컴파일러(neuronx-cc), 런타임, 프로파일링 도구, PyTorch/JAX 프레임워크 통합을 포함합니다.

🚗
비유: CUDA와 Neuron
NVIDIA GPU 생태계에 CUDA가 있듯, AWS 실리콘 생태계에는 Neuron이 있습니다. 모델(설계도)을 Trainium 칩(공장)에서 돌리려면 neuronx-cc(번역가)가 설계도를 그 공장의 작업대(NeuronCore)에 맞는 작업지시서로 바꿔줘야 합니다.
  • AWS Inferentia: 추론 전용 가속기. Inf1(초기 세대), Inf2(LLM 대상 성능 강화, NeuronLink로 분산 추론 지원)
  • AWS Trainium: 학습 전용으로 설계됐지만 추론에도 사용 가능. Trn1(대규모 학습용, GPU 대비 저비용), Trn2(더 강력한 성능, Trn2 UltraServer로 초대형 모델 학습)
  • NeuronCore: 칩 내부의 실제 연산 유닛(GPU의 SM과 비슷한 개념). Trn1 칩 1개당 NeuronCore-v2 2개.

관계 정리

AWS Neuron SDK (소프트웨어)
        │
        ├── Inferentia 칩 (추론용 하드웨어) ─┐
        │                                ├── 내부에 NeuronCore 여러 개 탑재
        └── Trainium 칩 (학습용 하드웨어)   ─┘

Neuron 소프트웨어 스택의 핵심 구성 요소:

  1. Neuron Compiler(neuronx-cc): 모델 그래프를 Neuron 실행 파일(.neff)로 정적 컴파일
  2. Neuron Runtime: 컴파일된 아티팩트를 디바이스에 로드, I/O 텐서 버퍼 할당, 칩 간 통신 오케스트레이션
  3. NKI(Neuron Kernel Interface): 저수준 커스텀 커널 작성용 인터페이스
  4. NxD(NeuronX Distributed): 대규모 모델을 여러 NeuronCore에 분산 배치하는 라이브러리 (NxD Core + NxD Inference)
  5. 도구: neuron-ls(토폴로지 조회), neuron-top(실시간 사용률), neuron-monitor(Prometheus/CloudWatch 연동)
📚 참고 자료: AWS Neuron 공식 문서[2] — Neuron은 Trainium/Inferentia용 컴파일러·런타임·프레임워크 통합 도구 묶음이며, Trn1 칩 1개에 NeuronCore-v2 2개라는 설명과 일치합니다.

네트워킹 구성 — Trainium 지원 AZ의 퍼블릭 서브넷 자동 탐색

VPC_ID=$(aws eks describe-cluster --name $CLUSTER_NAME --region $AWS_REGION --query 'cluster.resourcesVpcConfig.vpcId' --output text)
PUBLIC_ROUTE_TABLE=$(aws ec2 describe-route-tables --filters "Name=vpc-id,Values=$VPC_ID" "Name=route.destination-cidr-block,Values=0.0.0.0/0" --query 'RouteTables[0].RouteTableId' --output text)

SUPPORTED_AZS=($(aws ec2 describe-instance-type-offerings --location-type availability-zone --filters "Name=instance-type,Values=$INSTANCE_TYPE" --query 'InstanceTypeOfferings[*].Location' --output text))

VALID_SUBNETS=()
for az in "${SUPPORTED_AZS[@]}"; do
  subnet=$(aws ec2 describe-subnets --filters "Name=vpc-id,Values=$VPC_ID" "Name=map-public-ip-on-launch,Values=true" "Name=availability-zone,Values=$az" --query 'Subnets[0].SubnetId' --output text)
  [ "$subnet" != "None" ] && [ "$subnet" != "" ] && VALID_SUBNETS+=("$subnet")
done

[ ${#VALID_SUBNETS[@]} -lt 2 ] && { echo "Error: Need at least 2 public subnets in AZs that support $INSTANCE_TYPE"; exit 1; }

PUBLIC_SUBNET_1=${VALID_SUBNETS[0]}
PUBLIC_SUBNET_2=${VALID_SUBNETS[1]}
AZ_1=$(aws ec2 describe-subnets --subnet-ids $PUBLIC_SUBNET_1 --query 'Subnets[0].AvailabilityZone' --output text)
AZ_2=$(aws ec2 describe-subnets --subnet-ids $PUBLIC_SUBNET_2 --query 'Subnets[0].AvailabilityZone' --output text)

분석 노트 — NVIDIA GPU와 달리 전용 컨테이너 런타임이 필요 없는 이유
NVIDIA GPU는 컨테이너 런타임 레벨(nvidia-container-runtime 또는 CDI hook)이 개입해 드라이버 라이브러리를 컨테이너 안으로 주입해야 합니다. 반면 AWS Neuron은 커널이 이미 /dev/neuron0(칩 전체), /dev/ng0n1(코어 단위) 같은 디바이스 노드를 세분화해 노출하고, Neuron SDK는 pip 패키지로 컨테이너 이미지 안에 이미 포함되어 있어서 표준 runc만으로 충분합니다. 대신 "어떤 코어를 어떤 파드에 줄지"는 Neuron 전용 커스텀 스케줄러(my-scheduler)가 담당합니다.

Neuron device plugin 재설치 + Scheduler Extension 설치[6]

Neuron-optimized AMI가 자동 설치한 neuron-device-plugin은 Helm 소유(annotation)가 아니라서, scheduler.enabled=true 옵션으로 재배포하려면 충돌이 납니다. 기존 것을 지우고 Helm으로 다시 설치합니다.

kubectl delete daemonset neuron-device-plugin -n kube-system
kubectl delete clusterrole neuron-device-plugin
kubectl delete serviceaccount neuron-device-plugin -n kube-system
kubectl delete clusterrolebinding neuron-device-plugin

helm upgrade --install neuron-helm-chart oci://public.ecr.aws/neuron/neuron-helm-chart --set "npd.enabled=false"
kubectl get ds neuron-device-plugin -n kube-system
kubectl get nodes "-o=custom-columns=NAME:.metadata.name,NeuronCore:.status.allocatable.aws\.amazon\.com/neuroncore"

helm upgrade --install neuron-helm-chart oci://public.ecr.aws/neuron/neuron-helm-chart \
    --set "scheduler.enabled=true" \
    --set "npd.enabled=false"

kubectl get deploy -n kube-system k8s-neuron-scheduler
kubectl get deploy -n kube-system my-scheduler

이건 Helm 문법이 아닙니다 — --set 뒤에는 key=value가 와야 합니다. 대신 아래처럼 server.prefixURL/server.baseURL을 values 파일에 선언해서 적용하세요 (차트 버전에 따라 실제 values 키가 다를 수 있으니 helm show values prometheus-community/prometheus로 먼저 확인하는 것이 안전합니다): 
cat >> prometheus-values.yaml <<'EOF'
server:
  prefixURL: /p8s
  baseURL: http://<YOUR_INGRESS_ELB_DNS>/p8s/
EOF
helm upgrade prometheus prometheus-community/prometheus -n monitoring --reuse-values --values prometheus-values.yaml
⚠ 주의 — extraArgs에도 같은 플래그를 같이 넣지 마세요 ("flag 'web.route-prefix' cannot be repeated" 에러 재현 확인): deploy.yaml[12]을 보면 차트는 server.extraArgs를 먼저 전부 --key=value 형태로 펼친 뒤, 그것과 별개로 server.prefixURL이 있으면 --web.route-prefix={{ .Values.server.prefixURL }}를, server.baseURL이 있으면 --web.external-url={{ .Values.server.baseURL }}를 컨테이너 args 맨 뒤에 추가로 붙입니다. 즉 extraArgs.web.route-prefix와 server.prefixURL을 동시에 설정하면 --web.route-prefix가 args에 두 번 들어가고, Prometheus 바이너리의 플래그 파서가 중복을 허용하지 않아 flag 'web.route-prefix' cannot be repeated 에러로 컨테이너가 뜨지 못합니다. 해결책: 이 두 플래그는 반드시 extraArgs가 아니라 위 예시처럼 prefixURL/baseURL 전용 키로만 설정하세요(이미 extraArgs.web.route-prefix/web.external-url을 넣었다면 helm upgrade 전에 values 파일에서 삭제해야 합니다). extraArgs는 이 두 플래그처럼 전용 키가 없는 다른 옵션에만 사용하세요.

이렇게 server.prefixURL 하나로만 설정하면 좋은 점이 하나 더 있습니다 — 이 차트의 liveness/readiness probe 경로(path: {{ .Values.server.prefixURL }}/-/healthy, .../-/ready)도 같은 값을 그대로 읽어서 만들어지므로, probe 경로를 따로 맞춰줄 필요 없이 자동으로 일치합니다. 적용 후에는 아래처럼 실제로 Pod가 Ready인지 확인하세요.

kubectl get pod -n monitoring -l app=prometheus,component=server
# READY 1/1 이어야 정상. 0/1이면 events를 확인하세요.

자체 부하테스트 스크립트

#!/usr/bin/env python3
import requests, time, concurrent.futures, statistics
from datetime import datetime

class VLLMLoadTester:
    def __init__(self, base_url, max_workers=10):
        self.base_url = base_url.rstrip('/')
        self.max_workers = max_workers
        self.results = []

    def single_request(self, request_id):
        start_time = time.time()
        try:
            response = requests.post(
                f"{self.base_url}/completions",
                headers={"Content-Type": "application/json"},
                json={
                    "model": "tinyLlama/TinyLlama-1.1B-Chat-v1.0",
                    "prompt": f"Request {request_id}: Tell me about artificial intelligence",
                    "max_tokens": 100, "temperature": 0.7
                }, timeout=60)
            end_time = time.time()
            if response.status_code == 200:
                return {"request_id": request_id, "status": "success",
                        "latency": end_time - start_time,
                        "tokens": len(response.json().get("choices", [{}])[0].get("text", "").split())}
            return {"request_id": request_id, "status": "error", "latency": end_time - start_time,
                    "error_code": response.status_code}
        except Exception as e:
            return {"request_id": request_id, "status": "exception", "latency": time.time() - start_time, "error": str(e)}

    def run_load_test(self, total_requests=50):
        with concurrent.futures.ThreadPoolExecutor(max_workers=self.max_workers) as executor:
            futures = [executor.submit(self.single_request, i) for i in range(total_requests)]
            for future in concurrent.futures.as_completed(futures):
                self.results.append(future.result())
        self.analyze_results()

    def analyze_results(self):
        successful = [r for r in self.results if r["status"] == "success"]
        latencies = [r["latency"] for r in successful]
        tokens = [r.get("tokens", 0) for r in successful]
        print(f"Total: {len(self.results)} Success: {len(successful)}")
        print(f"Average Latency: {statistics.mean(latencies):.2f}s")
        print(f"95th Percentile: {sorted(latencies)[int(len(latencies)*0.95)]:.2f}s")
        print(f"Tokens per Second: {sum(tokens)/sum(latencies):.1f}")

if __name__ == "__main__":
    import sys
    tester = VLLMLoadTester(sys.argv[1], int(sys.argv[3]) if len(sys.argv) > 3 else 5)
    tester.run_load_test(int(sys.argv[2]) if len(sys.argv) > 2 else 30)

Lab6 — HPA와 KEDA

목표: CPU 사용률 기반 HPA를 구성하려 했으나, 원문에서는 실습 계정의 vCPU 쿼터 제한(8 vCPU)으로 2번째 노드를 추가하지 못해 실제 오토스케일 동작 실습은 생략되고 개념 설명으로 대체되었습니다.

⚠ KEDA GPU Scaler는 이 워크샵에 적용할 수 없습니다: keda-gpu-scaler[16]는 NVML C 바인딩으로 NVIDIA GPU 메트릭을 직접 읽는 KEDA External Scaler[17] 구현체입니다. AWS Neuron/Trainium은 NVML을 지원하지 않으므로 이 스케일러를 그대로 쓸 수 없습니다. 아래 내용은 "왜 CPU/메모리 기반 HPA가 AI 추론에 잘 안 맞는지"와 "GPU 환경의 대안"을 보여주는 참고 자료로만 다룹니다.

AFTER:  GPU Pod → keda-gpu-scaler (NVML) → KEDA → HPA               (2개 컴포넌트, 서브초 단위)
