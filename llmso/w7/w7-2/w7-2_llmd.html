Core 아키텍처
InferencePool
같은 모델을 서빙하는 vLLM/SGLang 파드들을 라벨로 그룹화하는 llm-d의 핵심 CRD. "인력파견회사의 명부"처럼 지금 어떤 파드가 대기 중이고 어느 EPP에게 배정을 물어야 하는지 항상 최신 상태로 유지한다.
EPP (Endpoint Picker)
llm-d 배포의 "두뇌". Envoy의 ext_proc 필터로 매 요청마다 호출되어, KV 캐시 상태·큐 깊이·부하를 실시간으로 채점해 최적 파드를 고르는 컴포넌트.
Router (Proxy + EPP)
llm-d의 지능형 라우터. Proxy(Envoy 등, 데이터플레인)와 EPP(라우팅 지능)가 분리된 2단 구조. Proxy는 "누구에게 보낼지 모른 채" 요청을 붙잡고 있다가 EPP가 정답을 알려주면 전달한다.
Model Server
실제로 GPU에 모델을 올려 추론을 수행하는 계층(vLLM/SGLang/TensorRT-LLM). Router/EPP가 내린 라우팅 결정의 최종 도착지.
라우팅·스케줄링 파이프라인
Filter → Score → Pick (공식 문서 표현)
llm-d 공식 문서(architecture/core/router/epp/scheduling)가 정의하는 EPP Request Scheduler의 정식 3단계 파이프라인. 후보 제거(Filter) → 점수 부여(Score) → 최종 1개 선택(Pick).
Scrapers → Filters → Scorers → Picker (강연 프레이밍)
Red Hat Ravindra Patil의 유튜브 강연에서 쓰인 개념적 설명 용어. 공식 문서 용어가 아니라 발표자가 메트릭 수집 단계(Data Layer 역할)를 별도로 "Scrapers"라고 부른 것 — 이 문서에서는 이 두 표현을 혼용하지 않고 구분해서 사용한다.
Flow Control
EPP 내부에서 모델 서버 풀을 과부하로부터 지키는 큐 게이트웨이. Priority Band → Fairness → Ordering 3계층 디스패치로 Noisy Neighbor·우선순위 역전을 방지한다.
SaturationDetector
Flow Control이 "지금 풀이 포화 상태인지"를 판단하는 게이트키퍼. utilization-detector(실시간 텔레메트리)와 concurrency-detector(활성 요청 카운팅) 두 방식이 있다.
KV 캐시 3종
Prefix-Cache Aware Routing
이미 관련 KV 캐시를 갖고 있는 파드로 요청을 우선 라우팅해 재계산을 없애는 기능. 근사(해싱 추정) / 정밀(ZMQ 이벤트 기반) 두 방식이 있다.
KV-Cache Indexer
모델 서버들이 ZMQ로 방출하는 BlockStored/BlockRemoved/AllBlocksCleared 이벤트를 구독해, 각 파드가 어떤 KV 캐시 블록을 보유하는지 실시간으로 추적하는 라우터 컴포넌트.
KV-Cache Offloading
GPU HBM 용량 한계를 넘어서기 위해 KV 캐시 블록을 CPU DRAM이나 공유 스토리지(SSD)로 옮기는 기술. vLLM 네이티브 커넥터 또는 LMCache/Mooncake 같은 외부 커넥터로 구현된다.
Disaggregated Serving (P/D 분리)
하나의 요청을 Prefill(프롬프트 처리) 단계와 Decode(토큰 생성) 단계로 분리해 서로 다른 전용 워커가 처리하게 하는 서빙 방식. 라우터가 두 엔드포인트를 각각 고르고 KV 캐시 전송까지 조율한다.
네트워킹 · 프로토콜
GAIE (Gateway API Inference Extension)
Kubernetes Gateway API를 추론 워크로드에 맞게 확장한 표준. InferencePool/InferenceObjective 같은 CRD와 Endpoint Picker Protocol을 정의하며, llm-d의 EPP는 이 표준의 실제 구현체다.
ext_proc
Envoy의 External Processing 필터. 매 요청마다 외부 gRPC 서비스(EPP)를 호출해 요청/응답을 가공(여기서는 "어디로 보낼지 결정")하게 하는 메커니즘. FULL_DUPLEX_STREAMED 모드로 스트리밍 응답도 그대로 통과시킨다.
ORIGINAL_DST 클러스터
Envoy의 특수 클러스터 타입. 고정 엔드포인트 목록 없이 매 요청마다 목적지를 동적으로 결정한다. EPP가 x-gateway-destination-endpoint 헤더에 심어준 값 그대로 연결해, 로드밸런싱 결정을 EPP에 100% 위임한다.
GPU · Kubernetes 실습 도구
HAMi (vGPU 분할)
물리 GPU 1장을 여러 컨테이너가 코어/메모리 비율(%) 단위로 나눠 쓰게 하는 CNCF Incubating 프로젝트. 이 실습에서는 GPU 1장을 두 vLLM 파드에 50%/50%씩 분할한다.
K3s
경량 단일 바이너리 Kubernetes 배포판. 이 실습에서는 traefik/servicelb를 비활성화하고 MetalLB로 대체한다.
MetalLB
베어메탈/온프렘 환경에서 LoadBalancer 타입 Service에 실제 IP를 할당해주는 소프트웨어 로드밸런서. IPAddressPool + L2Advertisement로 동작한다.
runai_streamer (S3 스트리밍 로더)
vLLM이 모델 가중치를 로컬 디스크에 통째로 복사하지 않고 S3(MinIO)에서 스트리밍으로 읽으며 GPU 메모리로 바로 로드하게 하는 로더. --load-format runai_streamer로 활성화한다.

핵심 요약 (3줄)
  1. llm-d는 vLLM/SGLang 같은 단일 노드 추론 엔진을 대체하지 않고 그 위에 얹어, 여러 노드·여러 GPU에 걸친 라우팅·오토스케일링·관찰성을 표준 패턴으로 제공하는 CNCF Sandbox 프로젝트다. 핵심은 Router(Proxy+EPP)가 KV 캐시 위치·큐 깊이·부하를 실시간으로 채점해 "가장 적합한 파드"로 매 요청을 라우팅하는 지능형 스케줄링이다.
  2. EPP(Endpoint Picker)는 Envoy의 ext_proc 필터를 통해 매 요청마다 호출되는 "배포의 두뇌"로, Filter→Score→Pick 파이프라인(prefix-cache-scorer, kv-cache-utilization-scorer, queue-scorer 등)을 거쳐 최적 파드를 고르고, ORIGINAL_DST 클러스터 타입 + x-gateway-destination-endpoint 헤더로 Envoy에게 그 결정을 100% 위임한다.
  3. 이 문서 Part B에서는 K3s+GPU 환경에 vLLM(Qwen3-0.6B-FP8)을 HAMi로 vGPU 50%/50% 분할해 2개 파드로 띄우고, vLLM 자체 벤치마크(ShareGPT/Prefix-Caching CronJob)로 베이스라인을 잡은 뒤, Envoy Gateway → Agent Router → GAIE(InferencePool) → llm-d 커스텀 EPP로 이어지는 8-Phase 설치를 실제로 수행해 Precise Prefix-Cache-Aware Routing이 캐시 적중률을 실측 개선(63.9%→68.75%)하는 것까지 트레이싱으로 검증한다.

Intelligent Routing in action: Scorers, Filters, Request Control — 참고 블로그

per-Call Flow (즉, 모든 인입 요청마다 아래 과정을 거침):

  1. 클라이언트 요청은 IGW에 Envoy가 받음
  2. Envoy는 EPP(엔드포인트 선택기)로 넘김 — EPP 역할: KV 캐시 인식과 부하 인식 기능
    1. Scrapers: 모든 LLM 추론 풀 파드에 접속하여 모니터링(Queue 대기열, 사용 가능 KV캐시, 현재 부하량) 정보 확인 → 파드 사용 가능 확인
    2. Filters: Scrapers 정보를 전달받아 스케줄링 제외 파드 필터
    3. Scorers: 필터 이후 후보 파드들을 스코어링(스케줄링해도 괜찮은지, 과부하가 걸렸는지 등)
    4. EPP: '부하, KV 캐시 사용량, Queue 대기열' 같은 입력값을 바탕으로 필터가 전달한 파드 대상을 결정하고 해당 작업을 다시 Envoy에 넘김
  3. Envoy는 선택된 파드로 스케줄링한다.
📌 용어 주의 — "Scrapers"는 공식 문서 용어가 아니다: 위 4단계(Scrapers→Filters→Scorers→EPP)는 이 유튜브 강연자(Ravindra Patil)가 사용한 개념적 설명 프레이밍이다. llm-d 공식 문서(architecture/core/router/epp/scheduling[7])는 EPP Request Scheduler를 "Filter → Score → Pick" 3단계로 명시하며, "Scrapers"라는 용어를 쓰지 않는다. 강연의 "Scrapers"는 공식 문서의 Data Layer(메트릭 수집 계층, 13장 참고)가 하는 역할을 발표자가 별도로 이름 붙인 것으로 보인다. 이 문서에서는 이 두 표현을 섞어 쓰지 않고, "공식 문서 표현"과 "이 강연의 프레이밍"임을 매번 명시한다.

4. 참고: llm-d Envoy config 예시

참고 자료: llm-d envoy config example[11]를 실제로 확인했다. 이 파일은 llm-d 저장소의 "no-kubernetes-deployment" 가이드에 포함된 예시로, Kubernetes 없이도 Envoy + EPP만으로 llm-d 라우팅을 재현할 수 있음을 보여준다.

  • 클라이언트 → Envoy(:8081) → [ext_proc gRPC 호출: 어느 파드로 보낼지 결정] → 결정된 파드로 직접 프록시
  • 일반적인 k8s Service(L4, 연결 단위 로드밸런싱)와 달리, 매 요청마다 외부 프로세스(EPP)가 판단해서 목적지를 동적으로 지정하는 L7 라우팅

http_filters 핵심: ext_proc

http_filters:
  - name: envoy.filters.http.ext_proc
    typed_config:
      "@type": type.googleapis.com/envoy.extensions.filters.http.ext_proc.v3.ExternalProcessor
      grpc_service:
        envoy_grpc:
          cluster_name: ext_proc
          authority: localhost:9002
        timeout: 10s
      processing_mode:
        request_header_mode: SEND
        response_header_mode: SEND
        request_body_mode: FULL_DUPLEX_STREAMED
        response_body_mode: FULL_DUPLEX_STREAMED
        request_trailer_mode: SEND
        response_trailer_mode: SEND
      message_timeout: 1000s
  • 모든 요청 헤더와 응답 헤더를 EPP(localhost:9002, gRPC)에 전달(SEND)
  • 요청/응답 바디는 FULL_DUPLEX_STREAMED: 버퍼링 없이 스트리밍 중에도 양방향으로 실시간 전달. vLLM의 SSE 스트리밍 응답을 토큰 단위로 그대로 통과시키면서 EPP가 관찰할 수 있게 함(전체 응답을 기다렸다 처리하면 스트리밍 UX가 깨짐)
  • message_timeout: 1000s: EPP 응답을 최대 1000초까지 기다림(긴 생성 스트림 처리 고려)
  • EPP(External Processor)가 하는 일: 요청 헤더(모델명 등)를 보고 llm-d의 스케줄러 로직으로 "이 요청을 어느 vLLM 파드로 보낼지" 결정한다. 실제 llm-d는 각 파드의 KV 캐시 히트율, 큐 길이, GPU 사용률 같은 실시간 서빙 상태를 반영해서 결정한다(kube-proxy처럼 "어느 파드가 바쁜지 전혀 모르고 무작위로 연결하는" 방식과 정반대).

original_destination_cluster 핵심 트릭:

- name: original_destination_cluster
  type: ORIGINAL_DST
  lb_policy: CLUSTER_PROVIDED
  original_dst_lb_config:
    use_http_header: true
    http_header_name: x-gateway-destination-endpoint
  • type: ORIGINAL_DST는 Envoy의 특수 클러스터 타입으로, 고정된 엔드포인트 목록이 없고 매 요청마다 목적지를 동적으로 결정한다.
  • use_http_header: true + http_header_name: x-gateway-destination-endpoint: EPP가(ext_proc 단계에서) 요청 헤더에 x-gateway-destination-endpoint: <파드IP>:<포트>를 심어주면, Envoy는 그 헤더 값 그대로 해당 파드에 직접 연결한다.
  • 즉 로드밸런싱 결정을 Envoy의 표준 알고리즘(round-robin, least-request 등)이 아니라 EPP가 매 요청 단위로 100% 위임받아 내린다 → kube-proxy의 "연결 단위 무작위 배정 후 keep-alive로 고착" 문제가 구조적으로 발생할 수 없다(요청마다 헤더로 새로 지정하므로).
  • circuit_breakers.max_connections: 40000 등 매우 높은 값: 대량의 동시 스트리밍 연결(긴 LLM 응답들이 오래 열려있음)을 견디도록 사실상 제한을 해제한다.

ext_proc 클러스터 (EPP 자체로 가는 경로):

- name: ext_proc
  type: STATIC
  lb_policy: LEAST_REQUEST
  health_checks:
    - grpc_health_check: {service_name: "envoy.service.ext_proc.v3.ExternalProcessor"}
  load_assignment:
    endpoints: [{address: 127.0.0.1, port_value: 9002}]
  • EPP가 Envoy와 같은 호스트에 사이드카처럼 동거(127.0.0.1:9002)한다. 원본 파일 상단 주석에도 "Envoy and the EPP are colocated on the same host"라고 명시되어 있으며, 이 no-k8s 버전에선 TLS도 생략(같은 머신 내부 통신)한다.
  • 표준 gRPC 헬스체크로 EPP 생존 여부를 지속 확인한다.
  • HTTP/2 스트림 윈도우 크기 설정(initial_stream/connection_window_size)은 ext_proc의 양방향 스트리밍 gRPC 트래픽 처리량 조정용이다.

5. llm-d Architecture — 지능형 라우팅

참고 자료: llm-d Architecture 공식 문서[4]를 실제로 확인했다.

Core Components: Router, InferencePool, Model Server

  • Router: Proxy(고성능 L7, GAIE 표준) + EPP(Endpoint Picker) — 실시간 메트릭·KV 캐시 친화성·정책으로 최적 파드를 실시간 채점/선택
  • InferencePool: 같은 모델을 서빙하는 파드들을 라벨로 그룹화(k8s 네이티브 discovery). 내부에 "Variant" 개념(prefill/decode 역할, 성능/비용별 부분집합)이 있음
  • Model Server: vLLM/SGLang 같은 실제 추론 엔진(GPU/TPU/HPU)

요청 흐름: 사용자 요청 → Router(Proxy) → EPP(실시간 채점) → 선택된 Model Server 파드 → 추론

고급 기능:

  • KV 캐시 3종 세트:
    1. Prefix-Cache Aware Routing(캐시 히트율 높은 파드로 라우팅)
    2. KV-Cache Indexing(모든 서버의 캐시 상태를 이벤트 기반 추적)
    3. KV Offloading(CPU/SSD로 캐시 계층 확장)
  • Disaggregated Serving: 하나의 요청을 Prefill/Decode 단계로 분리해 서로 다른 전용 워커가 처리 → 라우터가 두 엔드포인트를 각각 고르고 KV 캐시 전송까지 조율
  • 지연시간 예측 라우팅: XGBoost로 TTFT/ITL을 온라인 예측해서 SLO 기반 스코어링에 반영
  • 배치 추론: Batch Gateway(OpenAI 호환 배치 API) + Async Processor
  • 오토스케일링: EPP가 내보내는 큐 깊이 등 메트릭으로 HPA/KEDA 연동, 또는 비용 최소화하는 전역 최적화기(WVA)

6. [Core] InferencePool

참고 자료: InferencePool 공식 문서[5]를 확인했다.

📋
비유로 이해하기
InferencePool은 "인력파견회사의 명부"와 같다. 명부에는 지금 어느 직원(파드)이 대기 중인지, 어느 매니저(EPP)에게 배정을 물어봐야 하는지가 정리되어 있다. 직원이 늘거나 줄어도 명부는 항상 최신 상태로 자동 갱신된다.

"게이트웨이(Router) - EPP(Endpoint Picker) - 실제 모델 서버 파드들" 사이를 연결하는 중앙 리소스다. 파드 디스커버리와 게이트웨이/서비스메시 통합에 대한 "신뢰할 수 있는 단일 정보원(source of truth)" 역할을 한다.

해결하는 문제:

  • 모델 서버 파드가 스케일 인/아웃되며 계속 바뀌는 상황을 자동으로 감지
  • 게이트웨이와 EPP 사이에 필요한 메타데이터(어떤 파드, 어떤 포트, 어떤 EPP로 물어봐야 하는지)를 연결
  • 라우팅 정책을 중앙에서 관리

두 가지 역할:

  1. EPP를 위한 엔드포인트 디스커버리: selector(라벨 셀렉터)로 같은 네임스페이스 내 매칭되는 파드를 자동 탐색, 파드가 스케일링되거나 Ready 상태가 바뀌면 건강한 후보 목록을 자동 갱신, targetPorts로 실제 추론 트래픽이 나가는 포트(예: vLLM의 8000) 지정
  2. 게이트웨이 컨트롤러와의 서비스 연동: HTTPRoute의 backendRef로 쓰이면서, 프록시의 ext_proc 필터 설정을 담당 → envoy.yaml의 ext_proc cluster가 가리키는 EPP 주소를 여기서 제공하는 구조. EPP 응답을 기다리는 동안의 동작, 실패 시 정책(failureMode: FailOpen/FailClose)도 여기서 정의

핵심 필드:

spec:
  selector:              # 파드 검색용 라벨 셀렉터
  targetPorts:           # 포트 매핑
  endpointPickerRef:     # EPP 서비스 참조
  failureMode:           # EPP 실패 시 FailOpen/FailClose

멀티 InferencePool 시나리오:

  • 원칙: 보통 InferencePool 1개 = 모델의 논리적 배포 1개 = EPP 배포 1개
  • Prefill/Decode 분리: 서로 다른 InferencePool로 나눠서 각각 독립적으로 스케일링
  • 멀티 모델/버전: 모델 버전별로 InferencePool을 나눠 관리
  • 격리 원칙: 파드/EPP 서비스/InferencePool 간의 모든 참조는 같은 네임스페이스 내로 엄격히 제한 — 멀티테넌트 환경에서 경계를 분명히 함

7. [Core] llm-d Router

참고 자료: llm-d Router 공식 문서를 확인했다.

핵심 정의: 단순 로드밸런서가 아니라 "LLM을 이해하는 지능형 라우터"다. 일반적인 L7 프록시는 커넥션 수/응답시간 정도만 보지만, llm-d Router는 KV 캐시 위치, 실시간 부하, 요청 우선순위까지 반영해 요청을 배치한다.

구성: Proxy + EPP 분리 설계

  • Proxy: Envoy/Istio 등 검증된 L7 프록시. TLS 종료, 커넥션 관리, 실제 트래픽 전달(데이터 플레인) 담당
  • EPP(Endpoint Picker): 라우팅 "지능"을 담당하는 별도 서비스. 어디로 보낼지 "결정"만 함

요청 처리 흐름:

요청 도착 → Proxy가 요청을 잠시 "대기"시킴
        → ext_proc(External Processing)으로 EPP 호출
        → EPP가 InferencePool 상태를 평가해 최적 서버 선택
        → 선택된 주소를 Proxy에 반환
        → Proxy가 실제 요청을 그 서버로 전달

즉 Proxy는 "누구에게 보낼지 모른 채" 요청을 붙잡고 있다가, EPP가 정답(엔드포인트)을 알려주면 그제서야 전달한다. 이것이 앞서 envoy.yaml에서 봤던 ORIGINAL_DST + x-gateway-destination-endpoint 헤더 기반 클러스터 구조가 필요한 이유다.

라우팅 판단 기준: KV 캐시 위치성(prefix caching과 직결), 현재 부하(각 서버의 대기열/처리 능력), 요청 우선순위(중요도 기반 스케줄링)

확장 구조: Filters → Scorers → Pickers

  • Filters: 후보 서버 중 부적합한 것 제외
  • Scorers: 남은 후보들에 점수 매김(캐시 히트율, 부하 등)
  • Pickers: 최종 1개 선택

InferencePool과의 관계: Router(EPP)는 InferencePool이 제공하는 파드 목록/상태를 실시간으로 감시하고, 그 안에서 최적의 엔드포인트를 골라내는 소비자다. InferencePool = "누가 후보인가"(엔드포인트 디스커버리), Router/EPP = "그 중 누구를 고를 것인가"(지능형 선택 로직).

8. [Core] llm-d Router: Proxy

역할: Router의 실제 진입점. 클라이언트의 OpenAI 호환 요청을 받아, EPP가 골라준 모델 서버 pod로 전달하고, 응답을 다시 스트리밍해주는 데이터 플레인 담당자다.

지원 프록시 구현체: 자체관리형(Istio, agentgateway, Envoy AI Gateway), 클라우드관리형(Google Cloud Application Load Balancer)

요청 흐름 (ext_proc 기반):

클라이언트 → Proxy 수신
          → ext_proc 필터가 EPP 호출
          → EPP: Filters → Scorers → Pickers 파이프라인으로 최적 엔드포인트 결정
          → EPP가 엔드포인트 주소 반환
          → Proxy가 실제 모델 서버 pod로 전달
          → 응답을 Proxy 경유해 클라이언트로 스트리밍

두 가지 배포 모드:

  1. Standalone Mode
    • Proxy와 EPP가 같은 Pod 안에 사이드카로 배치
    • ext_proc이 localhost로 통신(네트워크 홉 없음)
    • 용도: 테스트, 레거시 Ingress, 배치 추론, RL 파이프라인
    • 장점: Gateway API 인프라가 아예 필요 없음

    설정 예시:

    apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
spec:
  gatewayClassName: istio
  listeners:
    - name: http
      protocol: HTTP
      port: 80
  2. Gateway Mode (Inference Gateway)
    • Kubernetes Gateway API(HTTPRoute, Gateway)를 정식으로 활용
    • 하나의 Gateway가 여러 HTTPRoute를 동시에 호스팅 가능
    • 가중치 기반 트래픽 분할, 트래픽 미러링, 멀티클러스터 로드밸런싱까지 지원 — 프로덕션급 규모용
    • 라우팅 계층: Gateway → HTTPRoute → InferencePool(또는 일반 Service)
      • InferencePool을 backendRef로 지정한 경로만 EPP를 거치는 "추론 인식형" 라우팅
      • 일반 Service로 지정된 경로는 그냥 표준 k8s 라우팅(EPP 관여 없음)

    설정 예시:

    # 즉 HTTPRoute가 "이 경로는 InferencePool로 보낼 요청이다"라고 표시해두면, 그 경로로 들어온 요청만 EPP 상담 절차를 거치게 됩니다.
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
spec:
  parentRefs:
    - kind: Gateway
      name: my-gateway
  rules:
    - backendRefs:
        - kind: InferencePool
          name: my-infpool
      matches:
        - path: {type: PathPrefix, value: /}

9. [Core] llm-d Router: EPP (Endpoint Picker)

참고 자료: EPP 공식 문서[6]를 확인했다. WebFetch로 재확인한 결과, EPP는 "llm-d 배포의 '두뇌'"로 정의되며, 두 가지 핵심 목표(지능형 라우팅, 공정성/우선순위 관리)를 가진다는 설명이 소스 문서와 정확히 일치했다.

정의: EPP는 "llm-d 배포의 두뇌"다. InferencePool(누가 후보인가)과 Proxy(어떻게 전달하는가) 사이에서, 실제로 "이 요청은 어느 파드로 보낼까"를 결정하는 유일한 컴포넌트다.

두 가지 핵심 목표:

  1. 지능형 라우팅: KV 캐시 사용률, 프리픽스 캐시 지역성, 큐 깊이, 활성 요청 수 등 실시간 내부 상태를 반영
  2. 공정성/우선순위 관리: 여러 워크로드(예: 실시간 채팅 vs 배치 요약)를 같은 모델 서버 풀에서 함께 돌릴 때 우선순위를 조율

요청 처리 6단계 파이프라인:

요청 도착 → 외부 처리(ext-proc) → 요청 핸들링 → 플로우 제어 → 요청 스케줄링 → 요청 프록시. 별도로 백그라운드에서 Data Layer가 k8s API와 메트릭을 비동기 수집한다.

컴포넌트:

  • Request Handler: 요청을 EPP 내부 구조로 변환. 기본: OpenAI HTTP, vLLM gRPC. 커스텀 파서 확장 가능
  • Flow Control: 과부하 방지 + 우선순위 큐잉. SaturationDetector(포화도 감지), FairnessPolicy(밴드 내 라운드로빈 등), OrderingPolicy(FIFO/SLO 기반)
  • Request Scheduler: 실제 파드 선택. Filter → Score → Pick 파이프라인, ProfileHandler가 전체 조율
  • Data Layer: 판단 근거 데이터 수집. k8s API(활성 파드), 모델 서버 상태(실행 큐, KV 캐시), 메모리 내 프리픽스 캐시 트리, "컨설턴트" 사이드카(지연시간 예측기, KV 인덱서, 토크나이저)

설정 방식: EndpointPickerConfig YAML을 --config-file 또는 --config-text 인자로 EPP 바이너리에 전달. 주의: 설정은 시작 시 1회만 읽힘 → 설정 변경 시 EPP 프로세스 재시작 필요(핫 리로드 없음).

통신 프로토콜: Proxy ↔ EPP는 Envoy ext-proc 프로토콜, 반드시 FULL_DUPLEX_STREAMED 모드. EPP → 백엔드 선택 규격은 Kubernetes Gateway API Inference Extension의 Endpoint Picker Protocol 표준을 준수한다.

10. [Core] EPP Request Handler

참고 자료: EPP Request Handling 공식 문서

역할: 추론 요청의 "생명주기 관리자". 요청이 들어와서 스케줄링되기 전까지, 그리고 응답이 스트리밍되는 동안의 파싱/추적을 전담한다.

3대 핵심 컴포넌트:

  • Parser: 원시 요청을 EPP 내부 구조화된 표현으로 변환, 응답에서 사용량(usage) 데이터 추출
  • DataProducer: 스케줄링에 필요한 상태 생성 — 토큰화, 캐시 매칭, 지연시간 예측 등
  • Admitter: SLO 기준 충족 여부 판단, 미충족 시 즉시 요청 반려

프로토콜 별 파서: openai-parser(OpenAI HTTP API - /chat/completions, /completions, /embeddings), vllmgrpc-parser(vLLM gRPC - Generate, Embed), passthrough-parser(범용, 페이로드 해석 없음 — 페이로드 기반 스케줄링은 불가)

처리 흐름: 요청 → Parser(형식 파싱) → DataProducer(상태 생성) → Admitter(SLO 검증) → Request Scheduler(파드 선택) → Model Server(실행) → ResponseBodyProcessor(응답 추적)

제공되는 기본 플러그인:

  • DataProducer: predicted-latency-producer(XGBoost로 TTFT/TPOT 예측), inflight-load-producer(엔드포인트별 진행 중 요청/토큰 수 추적), approx-prefix-cache-producer(프롬프트 해싱 기반 캐시 매칭)
  • Admitter: latency-slo-admitter(SLO 미충족 시 낮은 우선순위 요청 거부)
  • 확장 훅(자동 와이어링): PreRequest(처리 시작 전), ResponseHeaderProcessor(응답 헤더 수신 시), ResponseBodyProcessor(스트리밍 중/완료 시 사용량 추적)

주요 메트릭: llm_d_epp_request_total/llm_d_epp_request_running(요청량/동시 실행 수), llm_d_epp_request_ttft_seconds/llm_d_epp_request_streaming_tpot_seconds(지연시간), llm_d_epp_request_input_tokens/llm_d_epp_request_cached_tokens(토큰/캐시 히트)

11. [Core] EPP Flow Control

참고 자료: EPP Flow Control 공식 문서

역할: EPP 내부에서 모델 서버 풀을 과부하로부터 지키는 중앙 큐 게이트웨이다. 일반적인 RPS 기반 제한과 달리, LLM 서빙 특유의 비선형적 리소스 소비(긴 컨텍스트, 자기회귀 디코딩)를 고려해 설계됐다.

🎢
비유로 이해하기
Flow Control은 "놀이공원의 패스트트랙 + 대기줄 시스템"과 같다. VIP(우선순위 높은 요청)는 앞으로 보내고, 일반 손님(sheddable 요청)은 놀이공원이 너무 붐비면 입장을 아예 막을 수도 있다.

해결하려는 문제: Noisy Neighbor(큰 프롬프트를 던지는 테넌트가 KV 캐시를 독점), 스케줄링 후회(일단 디스패치하면 재라우팅 불가), 우선순위 역전(낮은 우선순위 배치 작업이 중요 요청을 막음), 리소스 비대칭(컨텍스트 크기 차이가 극심함)

3계층 디스패치 구조 (FlowKey = FairnessID + Priority):

  • Tier 1: Priority Band — 역할(최우선 대역 선택), 제어 방식(고정)
  • Tier 2: Fairness — 역할(대역 내 테넌트/플로우 선택), 제어 방식(FairnessPolicy 플러그인)
  • Tier 3: Ordering — 역할(플로우 내 개별 요청 순서), 제어 방식(OrderingPolicy 플러그인)

우선순위 요청 예시 (음수 우선순위 = "생략 가능(sheddable)" 요청, 헤더 없으면 우선순위 0 기본값으로 폴백):

curl -X POST http://${IP}:${PORT}/v1/completions \
  -H 'Content-Type: application/json' \
  -H 'x-llm-d-inference-fairness-id: tenant-a' \
  -H 'x-llm-d-inference-objective: premium-traffic' \
  -d '{
    "model": "default-model",
    "prompt": "Say hello"
  }'

FairnessPolicy / OrderingPolicy 플러그인:

구분플러그인동작
Fairnessround-robin-fairness-policy활성 플로우를 순회 처리
Fairnessglobal-strict-fairness-policy플로우 격리 무시, 전역 순서 엄격 적용
Orderingfcfs-ordering-policy도착 순서(FCFS)
Orderingedf-ordering-policy최소 데드라인 우선(EDF)
Orderingslo-deadline-ordering-policyx-llm-d-slo-ttft-ms 헤더 기반 SLO 데드라인

SaturationDetector (포화도 감지 = 게이트키퍼):

플러그인방식장단점
utilization-detector폐루프(실시간 텔레메트리)정확하지만 지연 존재
concurrency-detector개루프(활성 요청 카운팅)즉각적이나 실제 메모리 압력은 모름

Flow Control이 켜져 있으면 포화 시 디스패치를 멈추고 중앙 큐에 버퍼링하고, 꺼져 있으면 음수 우선순위 요청만 즉시 429로 거부한다.

설정 예시:

  - type: round-robin-fairness-policy
  - type: fcfs-ordering-policy

    parameters: {maxConcurrency: 15, concurrencyMode: requests}
saturationDetector:
  pluginRef: concurrency-detector
flowControl:
  maxBytes: "10Gi"
  maxRequests: "1k"
  defaultRequestTTL: "60s"
  priorityBands:
    - priority: 100
      maxRequests: "500"
      fairnessPolicyRef: round-robin-fairness-policy
      orderingPolicyRef: fcfs-ordering-policy

파이프라인 위치: Request Handler(파싱/헤더추출) → Flow Control(큐잉/포화게이팅) → Request Scheduler(엔드포인트선택) → Model Servers

12. [Core] EPP Request Scheduler

참고 자료: EPP Request Scheduler 공식 문서

역할: EPP 파이프라인의 마지막 결정 단계. Flow Control을 통과한 요청에 대해 실제로 "이 파드로 보낸다"를 확정한다. 실시간 메트릭, 프리픽스 캐시 상태, LoRA 어댑터 유무까지 고려한 플러그인 기반 파이프라인이다.

📌 공식 문서 표현: Filter → Score → Pick 3단계 (앞서 3장 강연 프레이밍의 Scrapers/Filters/Scorers와는 다른 층위의 설명이다 — 공식 명칭은 이 3단계뿐이다.)
  1. Filter: 부적절한 후보 제거
    플러그인기능
    prefix-cache-affinity-filter프리픽스 캐시 점수 높은 "sticky" 엔드포인트 우선 선택, 느리면 제외
    slo-headroom-tier-filterSLO 여유(헤드룸) 기준 필터링
    label-selector-filter레이블 셀렉터 매칭 엔드포인트만 유지
    prefill-endpoints-filter / decode-endpoints-filterP/D 분리 시 역할별 필터링
  2. Score: 0.0~1.0 점수 부여
    플러그인스코어링 근거
    kv-cache-utilization-scorerKV 캐시 사용률 낮을수록 고점
    latency-scorer예측 지연시간과 SLO 간 여유
    lora-affinity-scorer요청 LoRA 어댑터가 이미 로드된 엔드포인트 선호
    prefix-scorer프리픽스 캐시 일치 길이
    queue-depth-scorer대기열 짧을수록 고점
    running-requests-size-scorer활성 요청 수
    token-load-scorer처리 중인 전체 토큰량
    session-affinity-scorer같은 세션의 이전 요청을 처리했던 엔드포인트 최고점
    no-hit-lru-scorer캐시 미스 요청을 아직 안 받은 엔드포인트에 우선권(prefill 부하 균등화)

    점수 합산: 가중치 곱 합산. 예) Scorer A(가중치2.0)=0.8, Scorer B(가중치1.0)=0.5 → 최종 = 0.8×2.0 + 0.5×1.0 = 2.1

  3. Pick: 최종 선택
    플러그인전략
    max-score-picker (기본값)최고 점수 1개 선택
    random-picker무작위 선택
    weighted-random-picker점수를 확률로 쓰는 가중 추첨

SchedulingProfile / ProfileHandler: 각 SchedulingProfile = Filters 목록 + WeightedScorer 목록 + Picker 1개. ProfileHandler가 어떤 프로필을 실행할지 결정한다.

  • single-profile-handler: 단일 프로필 실행(일반적인 경우)
  • disagg-profile-handler: Prefill/Decode용 프로필 2개를 분리 실행
  • (deprecated) pd-profile-handler, data-parallel-profile-handler: 각각 위 둘로 대체 권장

Prefill/Decode Disaggregation 흐름:

  1. ProfileHandler가 Prefill 프로필과 Decode 프로필을 각각 실행
  2. Prefill 프로필: 프리픽스 캐시 친화도, 큐 깊이 중시
  3. Decode 프로필: 메모리 대역폭 바운드 워크로드 최적화
  4. 최종적으로 decode 엔드포인트가 proxy의 실제 목적지가 되고, prefill 엔드포인트는 헤더로 주입되어 decode 워커의 사이드카가 원격 prefill을 조율

설정 예시:

scheduler:
  profileHandler:
    type: single-profile-handler
    primaryProfile:
      filters:
        - type: prefix-cache-affinity-filter
          stickinessThreshold: 0.7
      scorers:
        - {name: kv-cache-scorer, weight: 2.0}
        - {name: latency-scorer, weight: 1.5}
        - {name: queue-depth-scorer, weight: 1.0}
      picker:
        type: max-score-picker
        maxNumOfEndpoints: 1

주요 메트릭: llm_d_epp_ready_endpoints, llm_d_epp_average_kv_cache_utilization, llm_d_epp_average_queue_size(풀 전체 건강 상태), llm_d_epp_scheduler_e2e_duration_seconds, llm_d_epp_plugin_duration_seconds(스케줄링 성능), llm_d_epp_disagg_decision_total(P/D 라우팅 결정 통계)

13. [Core] EPP Data Layer

참고 자료: EPP Data Layer 공식 문서

역할: EPP 파이프라인의 실시간 상태 수집·저장 계층이다. 큐 깊이, KV 캐시 사용률, LoRA 어댑터 상태 같은 원시 데이터를 모아서, Request Scheduler와 Flow Control이 참조할 수 있는 형태로 제공하는 "데이터베이스"다.

데이터 생명주기: Source → Extractor → Endpoint Attributes

각 Endpoint(파드)마다 스레드세이프·타입세이프 속성 맵을 유지하고, 여기에 수집된 값들을 채워 넣는 구조다.

3가지 데이터 소스 유형:

유형방식구현 예시수집 대상
Polling Data Sources설정된 주기로 폴링metrics-data-source → core-metrics-extractorKVCacheUsagePercent, WaitingQueueSize 등
Notification Sourcesk8s 리소스 변경 이벤트 감지k8s-notification-source → NotificationExtractorPod/Service 변경
Endpoint Event Sources엔드포인트 생명주기 이벤트endpoint-notification-source → EndpointExtractor파드 추가/삭제/업데이트

Polling 방식은 "런타임이 신규 엔드포인트마다 Collector를 하나씩 띄우고, 설정된 간격으로 해당 소스를 폴링"하는 구조다.

주요 플러그인: metrics-data-source(Prometheus 호환 메트릭 파싱), core-metrics-extractor(엔진별(vLLM 등) 메트릭 이름을 표준 키로 변환해 속성으로 저장)

Scheduler/Flow Control과의 관계: Data Layer는 수집만 담당하고, 그 값을 읽어 실제 판단(필터링/스코어링/큐잉)을 내리는 건 Request Scheduler와 Flow Control의 몫이다. 즉 이 레이어는 "판단 근거를 준비하는" 순수 데이터 파이프라인이다.

확장 방법: 새 데이터 소스를 추가하려면 세 인터페이스 중 하나를 구현하면 된다: PollingDataSource, NotificationSource, EndpointSource.

14. [Core] EPP Configuration (EndpointPickerConfig)

참고 자료: EPP Configuration 공식 문서

핵심 성격: k8s CRD처럼 생겼지만 실제 CRD는 아니고, EPP 프로세스가 시작 시점에 한 번만 읽는 정적 설정 파일이다. 지금까지 본 모든 플러그인(Filter, Scorer, Picker, FairnessPolicy, OrderingPolicy, DataProducer 등)을 이 하나의 YAML로 정의한다.

전체 스키마 골격:

apiVersion: llm-d.ai/v1alpha1
kind: EndpointPickerConfig
plugins: [...]            # 모든 플러그인 인스턴스 정의(그래프의 "노드")
featureGates: [...]       # 예: flowControl
parser: {...}             # 요청 파싱 방식
flowControl: {...}
saturationDetector: {...}
schedulingProfiles: [...]
dataLayer: {...}

설계 철학: 그래프 기반 (노드-엣지): 노드 = plugins 섹션에 정의된 개별 플러그인 인스턴스, 엣지 = schedulingProfiles, flowControl 등에서 pluginRef로 그 플러그인을 참조하는 연결. 같은 플러그인 인스턴스를 여러 프로필/우선순위 대역에서 재사용 가능하다.

plugins:
  - name: my-scorer
    type: prefix-cache-scorer
    parameters: {blockSizeTokens: 64}

name 생략 시 type이 곧 이름이 된다. Admitter/DataProducer 인터페이스 구현 플러그인은 Auto-Wiring되어 별도 참조 없이 자동 연결된다.

섹션별 핵심:

섹션핵심 내용
Feature Gates현재 flowControl만 명시적 활성화 필요. 제거 시 2-릴리스 deprecation 절차
Parser기본값 openai-parser, 변경 시 parser.pluginRef로 참조
Flow ControlmaxBytes/maxRequests/defaultRequestTTL(전역) + priorityBands(대역별 orderingPolicyRef/fairnessPolicyRef, 기본 fairness는 global-strict-fairness-policy)
Saturation Detector미지정 시 utilization-detector 자동 생성, pluginRef로 교체 가능
Scheduling ProfilesFilter→Score→Pick 목록. 프로필당 Picker는 정확히 1개만 허용(2개 이상이면 런타임 에러)
Data Layermetrics-data-source+core-metrics-extractor가 기본 자동 주입

Defaulting 규칙 (3단계):

  1. schedulingProfiles 자체를 생략 → 모든 Filter/Scorer/Picker를 포함한 default 프로필 자동 생성
  2. 프로필은 있는데 plugins가 빈 목록 → 유효하며, Picker만 자동 주입
  3. Picker 미지정 → max-score-picker(maxNumOfEndpoints: 1) 자동 주입

즉 아무 설정도 안 해도 합리적인 기본 동작을 하도록 설계되어 있다.

설정 전달 방법:

--config-file /etc/epp/epp-config.yaml   # 파일 기반, 보통 ConfigMap 마운트
--config-text "..."                      # 인라인 텍스트

검증 규칙 및 에러: pluginRef가 plugins에 없는 이름 참조 → 초기화 에러. 이름 중복 → 검증 실패. 프로필당 Picker 2개 이상 → 런타임 에러. DataProducer 간 순환 의존성 → DAG 검증 실패. 모두 시작 시점에만 검사됨 — 런타임 중 오류 감지/리로드 없음.

왜 재시작이 필요한가: "configuration is not reconciled by a controller" — EPP는 시작 시 전체 플러그인 그래프를 한 번 구성하고 끝난다. 컨트롤러가 지속 감시(reconcile)하는 구조가 아니라서 핫 리로드가 원천적으로 없다.

운영 권장사항: 배포 전 로컬에서 스키마/pluginRef 검증, HA 구성(replicas > 1 + leader 선출 → 롤링 재시작 시 무중단 전환), 모니터링(:9090/metrics, Prometheus, upstream 제공 대시보드 tools/dashboards/inference_gateway.json), 알림 규칙(P99 지연/에러율/큐 깊이/KV 캐시 사용률 사전 구성 권장), 기능 롤백은 Feature Gate 비활성화로 대응.

15. [Core] Model Servers

참고 자료: Model Servers 공식 문서

역할: llm-d 스택의 최하위 계층 — 실제로 GPU/TPU에 모델을 올리고 추론을 실행하는 컴포넌트다. 지금까지 본 Router/Proxy/EPP는 모두 "누구에게 보낼지" 결정하는 컨트롤 플레인이었고, Model Server가 바로 그 결정의 도착지, 즉 이 문서 Part B에서 계속 다룰 qwen3-0-6b-fp8 Deployment에 해당하는 계층이다.

지원 추론 엔진: vLLM, SGLang, TensorRT-LLM(trtllm-serve)

핵심 책임: OpenAI 호환 API 서빙(/v1/completions, /v1/chat/completions), 메트릭 노출(KV 캐시 사용률, 큐 깊이, 활성 요청 수), GPU 메모리 내 KV 캐시 관리 + 프리픽스 캐싱, 병렬화 전략 지원(TP/DP/EP)

EPP가 요구하는 필수 메트릭:

메트릭타입의미

InferencePool 통합: "모델 서버는 k8s 레이블 셀렉터를 통해 InferencePool에 자동 등록" → EPP가 헬스체크 확인 후 트래픽 라우팅 시작. Model Server 자체는 llm-d 스택의 나머지 부분과 완전히 독립적으로 배포된다.

16. [Capabilities] KV Cache Management

참고 자료: KV Cache Management 공식 문서[8]

목표: 중간 상태(KV 캐시)의 추적·재사용을 통한 지연시간 감소와 처리량 증가.

🍲
비유로 이해하기
KV 캐시는 "요리 중간 재료 보관"과 같다. 같은 재료(prefix)로 시작하는 요리를 매번 처음부터 준비하면 시간이 많이 걸리므로, 이미 손질된 재료를 캐시(KV 캐시)에 보관해두고 재사용하면 훨씬 빠르다.

3계층 아키텍처:

  1. Prefix-Cache Aware Routing (지능 계층): 앞서 봤던 Router/EPP가 담당하는 부분. 캐시 인덱스를 참고해 캐시 히트율이 최대가 되도록 요청을 라우팅. 구현 방식 2가지: 근사(heuristic) 기반(approx-prefix-cache-producer, 프롬프트 해싱 추정), 정밀(event-driven) 기반(precise-prefix-cache-producer, 실제 KV 캐시 상태 실시간 추적)
  2. KV-Cache Indexing (관찰성 계층): 풀 전체의 KV 캐시 상태를 지속 모니터링. vLLM 같은 엔진이 발생시키는 고빈도 이벤트를 소비해서 토큰 블록의 이동/제거를 추적. 정밀 라우팅 결정의 "source of truth" 역할 — Prefix-Cache Aware Routing의 정밀 모드가 참조하는 바로 그 데이터
  3. KV Offloading (용량 계층): GPU HBM(고대역폭메모리) 용량 한계를 극복하기 위해, 캐시 항목을 CPU 메모리 또는 로컬 SSD로 오프로드. 이렇게 다중 계층(HBM → CPU RAM → 로컬 디스크) 저장 구조를 형성

17. [Capabilities] Prefix-Cache Aware Routing

참고 자료: Prefix-Cache Aware Routing 공식 문서

핵심: EPP가 요청을 "이미 관련 KV 캐시를 갖고 있는 파드"로 우선 라우팅해서 불필요한 재계산을 없애고 지연시간을 줄이는 기능이다. prefix-cache-affinity-filter/prefix-scorer 동작의 내부 구현이며, 근사(Approximate)와 정밀(Precise) 두 방식이 있다. 선택 기준: 가볍게 시작하려면 근사, 정확도와 대규모 운영이 중요하면 정밀.

  1. 근사(Approximate) 방식
    • 구성: approx-prefix-cache-producer(데이터 생성) + prefix-cache-scorer(스코링)
    • 동작 원리: EPP엔 토크나이저가 없으므로 문자-토큰 비율로 근사 계산 → 프롬프트를 고정 크기 블록(예: 토큰 16개 단위)으로 나눠 롤링 해시 체인 구성 → EPP가 "최근 어느 프리픽스 해시를 어느 파드로 보냈는지" 메모리 내 LRU 인덱스로 자체 관리 → 매칭된 블록 비율로 점수 산정 → 라우팅 후 "이 파드가 이제 이 프리픽스를 갖고 있다"고 가정하고 인덱스 갱신(실제 확인 없이 추정)
    • 장점: 외부 의존성 없음, 가벼움, 토크나이저 사이드카·ZMQ 불필요
    • 단점: 파드 메모리 압박으로 실제 캐시가 제거돼도 EPP는 모름(상태 불일치), 문자 기반이라 정밀도 낮음
  2. 정밀(Precise) 방식
    • 구성: token-producer(정확한 토큰화) + precise-prefix-cache-producer(KV-블록 인덱스 소유) + prefix-cache-scorer + KV-Cache Indexer(Data Layer 컴포넌트)
    • 동작 원리: 프롬프트를 vLLM의 /v1/completions/render HTTP 엔드포인트로 보내 정확한 토큰 ID 획득(EPP 파드 내 사이드카 또는 공유 render 서비스) → 모델 서버가 KV 캐시 변경 시 ZeroMQ로 KVEvents 실시간 방출 → KV-Cache Indexer가 이 이벤트를 구독해 각 파드의 정확한 토큰 블록 위치를 전역 추적 → 각 후보 파드의 실제 토큰-ID 프리픽스 보유 현황으로 정밀 스코링 → 추측적 인덱싱(speculative indexing): 라우팅 결정 시점과 실제 KVEvent 도착 사이의 "암흑 시간(blind spot)"을 메우기 위해, 라우팅 직후 즉시 추정 항목을 인덱스에 선반영
    • 장점: 100% 정밀(토큰 기반), 복잡한 캐시 제거 정책도 정확히 처리, Prefill/Decode 분리 네이티브 지원
    • 단점: vLLM render 엔드포인트 + ZMQ 연결 필요, 약간의 리소스 오버헤드, 모델 서버가 KV 이벤트 방출을 지원해야 함

이 문서 Part B의 Phase 5에서 이 정밀(Precise) 방식을 실제로 활성화하고, /v1/completions/render 호출 로그와 ZMQ 구독 로그를 통해 정확히 이 동작 원리대로 작동함을 확인한다.

18. [Capabilities] KV-Cache Indexer

참고 자료: KV-Cache Indexer 공식 문서

핵심 목적: KV-Cache Indexer는 모델 서버 전반의 KV 캐시 상태를 실시간으로 파악하여, 정밀한 prefix-cache-aware 라우팅 기능을 제공하는 라우터 컴포넌트다.

주요 기능 - 다음 영역에서 정밀도 향상: 이미지/오디오 콘텐츠 해싱을 사용하는 멀티모달 모델, 비선형적인 KV 사용 패턴을 가진 하이브리드 어텐션 아키텍처, 단순 LRU 정책을 넘어선 고급 오케스트레이션

아키텍처 구성 요소 (협업하는 3가지 요소):

  1. Index (인덱스): 이벤트 기반 업데이트를 통해 블록 키(block key)를 파드 위치에 매핑
  2. Data Producer (데이터 생성기): 요청당 한 번씩 프롬프트를 토큰화하고 멀티모달 피처를 추출
  3. Scorer (스코어러): 파드별로 가장 긴 연속(consecutive) prefix 매치를 평가

이벤트 시스템: 모델 서버는 ZMQ를 통해 3가지 이벤트 유형을 발행한다 — BlockStored(새 캐시 블록 생성), BlockRemoved(블록 축출), AllBlocksCleared(파드 캐시 초기화)

전달 방식(Delivery Modes): 중앙집중형(Centralized, 단일 EPP 엔드포인트), 파드 디스커버리(Pod discovery, K8s 라벨을 이용한 다중 EPP active-active 방식)

인덱스 저장 백엔드:

백엔드사용 사례트레이드오프
In-Memory (기본값)대부분의 배포 환경고정 엔트리 크기; 최저 지연시간
Cost-Aware Memory가변 엔트리 크기바이트 단위 예산 지정 가능
Redis/Valkey영속적 상태 저장네트워크 홉 오버헤드 발생

스코어링 로직: 스코어러는 각 파드에 캐시된 요청 블록들 중 "가장 긴 연속 prefix"를 식별한다. KV-cache 블록은 의존성 체인(dependency chain)을 형성하기 때문에, 서버는 끊기지 않은 prefix만 재사용할 수 있다. 예: 블록 B0~B3을 보유한 파드 → 점수 4, B0/B1은 있지만 B2가 없는 파드 → 체인이 끊겨서 점수 2. 블록은 티어(tier)에 따라 가중치 적용(GPU=1.0, CPU=0.8).

예측적 인덱싱(Speculative Indexing): speculativeIndexing: true 설정 시, 라우팅 결정 직후 예측 엔트리가 즉시 삽입되며 기본 TTL은 2초다. 이를 통해 확인(confirmation) 이벤트가 도착하기 전에도 연속으로 들어오는 요청들이 어피니티(affinity)를 유지할 수 있다.

요약: KV-Cache Indexer는 vLLM/llm-d 기반 분산 서빙 환경에서, 각 파드가 어떤 KV 캐시 블록을 보유하고 있는지 이벤트 기반으로 추적하여, 요청을 prefix 캐시 적중률이 가장 높은 파드로 라우팅하는 컴포넌트다.

19. [Capabilities] KV-Cache Offloading

참고 자료: KV-Cache Offloading 공식 문서

핵심 개념: KV-Cache Offloading은 KV 블록을 CPU DRAM, 공유 스토리지 같은 더 저렴한(저비용) 계층으로 옮김으로써 GPU 메모리 용량의 한계를 확장하는 기술이다. 두 가지 확장성 문제를 해결한다: GPU HBM(고대역폭 메모리) 용량 제약, 인스턴스별로 캐시가 고립되는(isolated per-instance) 문제.

두 가지 통합 방식:

  1. 네이티브 방식 (vLLM OffloadingConnector): vLLM 스택에 내장된 기능. 블록을 CPU 계층 또는 공유 스토리지 계층으로 디스패치. 활성화: --kv-offloading-backend native --kv-offloading-size <GB>
  2. Out-of-tree 커넥터 (외부 방식): 서드파티 엔진 사용(LMCache, Mooncake, NVIDIA KVBM). 캐시 로직이 별도 프로세스/서비스에 존재. 표준 KV-cache 커넥터 API를 통해 통합

주요 컴포넌트:

  • CPU Offloading: GPU DMA를 이용한 비동기 전송, 스테이징 버퍼용 "고정(pinned) CPU 메모리" 사용, vLLM 0.12.0+에서 연속 메모리 레이아웃(contiguous memory layout) 지원 → 처리량 4~5배 향상
  • llm-d FS Backend: "파일시스템에 구애받지 않는(filesystem agnostic)" 커넥터, POSIX 호환 시스템에서 블록을 파일로 저장, 인스턴스 간 캐시 공유 및 재시작 후에도 지속성(persistence) 제공
  • MooncakeStoreConnector: 분산 시스템, 중앙 집중형 Master가 메타데이터/축출(eviction) 관리. Embedded(프로세스 내 DRAM 풀 사용) / Standalone-store(SSD 지원이 가능한 외부 클라이언트 방식) 두 가지 모드 지원

성능 가이드: CPU offloading은 "CPU DRAM 용량이 GPU HBM보다 크면 항상 활성화"하는 것이 권장됨. 스토리지 offloading은 캐시가 단일 노드 용량을 초과하거나 노드 간 공유가 가치 있을 때 유리함.

요약: GPU HBM의 한계를 넘어 KV 캐시를 CPU RAM이나 공유 스토리지로 오프로딩하는 방법을 다룬다. vLLM 내장 네이티브 커넥터와 LMCache/Mooncake/KVBM 같은 외부 커넥터 두 갈래로 나뉘며, 특히 Mooncake는 여러 vLLM 인스턴스 간 캐시를 공유하는 분산 방식(중앙 Master + Embedded/Standalone 모드)을 제공한다.

20. [Capabilities] Inference Payload Processor (IPP)

참고 자료: IPP 공식 문서

개요: Inference Payload Processor(IPP)는 라우팅 결정 전후로 추론 요청/응답 페이로드를 처리하는 플러그형(pluggable) 프레임워크다. 풀(pool) 레벨에서 동작하며, 어떤 InferencePool이 요청을 처리할지 결정하는 데 관여한다.

주요 기능: 라우팅 전(pre-routing, 요청 헤더/본문/트레일러 검사 및 수정), 응답 후(post-response, 응답 헤더/본문/트레일러 검사 및 수정), 활용 사례 지원(모델 인지 라우팅, 가드레일, 콘텐츠 필터링, 관측성 등)

기술 아키텍처: IPP는 Envoy의 External Processing(ext-proc) 프로토콜을 통해 프록시와 통합된다. 프로필 기반 플러그인 아키텍처: Plugins(특정 작업을 수행하는 모듈형 처리 단위), Profiles(처리 파이프라인을 구성하는 이름이 지정된 플러그인 모음), Profile Picker(요청 속성에 따라 실행할 프로필을 선택하는 컴포넌트)

요청 흐름:

  1. 클라이언트가 프록시로 추론 요청 전송
  2. 프록시가 ext-proc를 통해 IPP 호출
  3. IPP가 플러그인 파이프라인을 거쳐 처리하고 변경사항(mutation)을 반환
  4. 프록시가 변경사항을 적용하고 InferencePool로 라우팅
  5. EPP(External Processing Point)가 풀 내에서 최적의 파드 선택
  6. 모델 서버가 요청을 처리하고 응답

운영 세부사항: IPP는 독립적인 Kubernetes Deployment로 배포되며, 환경에 따라 통합 방식이 다르다 — Istio 환경(EnvoyFilter를 통해 ext-proc 삽입), GKE 환경(GCPRoutingExtension 리소스 사용). 모니터링은 9090 포트에서 노출되는 Prometheus 호환 메트릭을 통해 이루어진다.

21. llm-d-router vs Envoy AI Gateway(Agent Router) 비교

요약: 같은 "라우터"란 이름을 쓰지만 레이어가 다르다.

  • llm-d Router: 동일한 모델을 서빙하는 vLLM 파드 집합 내부에서 KV-cache 적중률·부하를 보고 최적의 파드를 고르는 추론 클러스터 내부 스케줄러
  • Agent Router(구 Envoy AI Gateway): OpenAI/Anthropic/Bedrock/Vertex/자체호스팅 vLLM 등 여러 외부 provider를 통합하는 에이전트/앱 앞단의 API 게이트웨이
  • 즉 경쟁 관계라기보다, Agent Router가 앞단(Edge) 게이트웨이, llm-d Router가 그 뒤 vLLM 클러스터 내부의 라우팅 엔진 역할로 함께 쓰일 수 있는 구조다.
  1. [Tier 2] llm-d Router
    • 목적: KV-Indexer/Offloader와 같은 llm-d 생태계의 일부로, "이 모델을 서빙하는 N개의 vLLM 파드 중 어디로 보낼지"를 결정
    • 구조: Proxy(데이터 플레인, L7 프록시가 요청을 받아 잠시 보류하고 ext-proc 프로토콜로 EPP에 콜백, Envoy/Istio/GCP ALB 등 다양한 구현체 지원), EPP(Endpoint Picker, 라우팅 엔진, 실시간 신호를 평가해 최적 파드 주소를 반환, Filter→Scorer→Picker 파이프라인 구조)
    • 배포 모드: 경량 모드(Envoy가 EPP와 같은 파드에서 자체 관리), 프로덕션 권장 모드(Kubernetes Gateway API 표준 사용, EPP가 InferencePool의 백엔드로 동작)
    • 특징: KV-cache/prefix-cache 인지 라우팅, 로드 인지 라우팅, 요청 우선순위·flow control → 동종(homogeneous) 모델 서빙 인프라 내부 최적화에 특화
  2. [Tier 1] Agent Router (구 Envoy AI Gateway)
    • 변경 이력: Envoy AI Gateway가 Envoy 프로젝트 산하에서 분리되어 Agentic AI Foundation(AAIF) 소속의 독립 프로젝트 "Agent Router"로 리브랜딩됨(2026년 6월 v1.0, 8월 v1.1 출시)
    • 구조: 2계층 — 설정 계층(Agent Router: provider, 자격증명, 라우팅 규칙, 도구, 한도 정의), 트래픽 계층(Envoy Proxy: 실제 요청 처리)
    • 핵심 기능: 통합 provider 접근(16개 provider로 라우팅), 트래픽 관리(fallback/failover, 모델명 가상화, 토큰 한도), 보안/자격증명(라우터가 한곳에서 관리·로테이션), MCP 도구 통합, 추론 인지 라우팅(Kubernetes InferencePool 지원 — 여기서 llm-d의 EPP와 연결점이 생김), 관측성(OpenTelemetry GenAI 컨벤션)
    • 배포: 로컬에서 aigw run 한 줄로 실행 → Kubernetes까지 설정 변경 없이 스케일

Job 구성 방식: CronJob(suspend: true)를 재사용 템플릿으로 사용

  • 일반 Job은 spec이 불변이라 재실행하려면 매번 새 이름으로 apply해야 함. "반복 실행"을 깔끔하게 지원하기 위해:
    • CronJob을 schedule 값은 있지만 suspend: true로 등록 → 스케줄에 의해 자동 실행되지 않고, 순수 템플릿으로만 사용
    • 실행할 때마다: kubectl create job --from=cronjob/vllm-bench-sharegpt vllm-bench-manual-$(date +%s) -n vllm → 매번 고유한 Job 이름 자동 생성, YAML 수정/재적용 불필요
    • ttlSecondsAfterFinished: 3600 — 완료된 벤치마크 Job은 1시간 후 자동 정리(반복 실행 시 Job 누적 방지)
    • backoffLimit: 0, restartPolicy: Never — 벤치마크 실패 시 자동 재시도 없이 바로 로그 확인 가능하게
📌 vLLM bench의 ShareGPT 샘플링은 seed로 초기화된 의사난수로 94,145개 대화 중 정렬/셔플 후 앞에서부터 num_prompts개를 뽑는 방식이라, seed가 같으면 어느 시점에 실행하든 항상 같은 순서로 같은 대화가 선택된다. ⇒ --seed $(date +%s)로 매번 다르게 요청 설정!

📌 이 트러블슈팅은 실전에서 누구나 겪을 수 있는 문제이며, 롤백 절차 자체가 이 실습의 핵심 교훈 중 하나다.

처음에 공식 예제의 envoy-gateway-values-addon.yaml만 단독 적용했다가 registered extension has no hooks specified 에러로 새 파드가 CrashLoopBackOff에 빠졌다. 원인은 이 addon 파일이 반드시 base envoy-gateway-values.yaml(Agent Router 컨트롤러를 extension hook으로 등록하는 필수 설정)과 함께 써야 하는 파일이었기 때문이다.

원인 분석: addon 파일은 InferencePool backendResources 등록만 담당하는 "추가 설정 조각"이고, extensionManager.hooks.xdsTranslator(어떤 컨트롤러를 xDS 후처리 훅으로 쓸지 정의하는 핵심 설정)는 base 파일에만 있다. addon만 단독 적용하면 Envoy Gateway는 "확장 등록은 됐는데 훅이 없다"는 모순된 상태가 되어 파드가 계속 재시작을 반복한다.

대응: 즉시 이전 정상 버전으로 롤백해 서비스 중단 없이(기존 파드가 계속 Running 상태 유지) 안정화한 뒤, base+addon 올바른 조합을 다시 적용해 해결했다. 이 과정에서 남은 stale ReplicaSet도 정리했다.

# (재현 개념 요약 — 원문에 정확한 커맨드 로그는 없으나 트러블슈팅 흐름은 다음과 같다)
# 1) 잘못된 단독 적용으로 문제 재현
helm upgrade -i eg oci://docker.io/envoyproxy/gateway-helm \
  --version v1.9.1 -n envoy-gateway-system \
  -f envoy-gateway-values-addon.yaml   # base 없이 addon만 적용 → CrashLoopBackOff

# 2) 즉시 이전 정상 리비전으로 롤백 (기존 파드는 계속 Running 유지)
helm rollback eg -n envoy-gateway-system

# 3) base + addon 올바른 조합으로 재적용
helm upgrade -i eg oci://docker.io/envoyproxy/gateway-helm \
  --version v1.9.1 -n envoy-gateway-system \
  -f envoy-gateway-values.yaml \
  -f envoy-gateway-values-addon.yaml

# 4) stale ReplicaSet 정리
kubectl get rs -n envoy-gateway-system
kubectl delete rs <stale-replicaset-name> -n envoy-gateway-system

교훈: Helm values 파일을 여러 개(base + addon)로 나눠 배포하는 컴포넌트는, 문서에 "반드시 함께 적용하라"는 문구가 있는지 먼저 확인해야 한다. 하나만 적용해도 helm 자체는 에러 없이 성공하지만(YAML 문법은 유효하므로), 런타임에 컨트롤러가 "설정 불일치" 에러를 내며 크래시하는 방식으로 뒤늦게 드러난다. 이런 상황에서는 무중단 원칙 — 문제 있는 새 리비전을 즉시 이전 리비전으로 롤백해 기존 트래픽 처리 파드를 살려두고, 그다음에야 원인을 분석하고 올바른 조합을 재적용 — 이 핵심이다.

해석:

  • 캐시 적중률은 명확히 개선됨(63.9% → 68.75%, 약 +4.9%p) — precise 라우팅이 동일 prefix 요청을 같은 파드로 더 적극적으로 몰아준 결과이며, 쿼리 분산 비율(62/38)에서도 이 어피니티 효과가 드러난다.
  • 반면 TTFT는 오히려 소폭 증가했다. 이는 Gateway(Envoy)→EPP(ext-proc gRPC 스코어링) 홉이 추가되면서 생기는 고정 오버헤드 때문으로 보이며, 이 모델(Qwen3-0.6B)의 TPOT가 이미 ~15ms로 매우 빨라 절대 지연시간이 작다 보니, 라우팅 오버헤드의 상대적 영향이 두드러지게 나타난 것으로 판단된다.
  • 즉, "파드 2개 + 작은 모델" 규모에서는 precise 라우팅의 캐시 이득이 라우팅 오버헤드를 상쇄할 만큼 크지 않을 수 있다는 것을 보여주는 결과다. Precise routing의 진짜 이점은 파드 수가 많아 라운드로빈이 우연히 캐시를 못 맞출 확률이 높아지는 환경(예: replica 8개 이상, 큰 모델로 cache-miss 재계산 비용이 큰 경우)에서 더 뚜렷하게 나타날 것으로 예상된다.

정리: 벤치마크 후 vllm-bench-prefix-caching CronJob 재개, 일회성 비교 Job들(vllm-bench-gateway-precise, vllm-bench-direct-baseline)은 ttlSecondsAfterFinished로 자동 정리됨.

  • spec.parentRefs: 이 HTTPRoute가 Phase 4에서 만든 Gateway/inference-gateway(MetalLB IP)에 소속됨을 선언. namespace를 명시하지 않았으므로 HTTPRoute와 같은 네임스페이스(vllm)의 Gateway를 참조(둘 다 vllm ns에 있어서 별도 ReferenceGrant 불필요 — 만약 서로 다른 ns였다면 cross-namespace 참조 허용을 위한 ReferenceGrant가 추가로 필요했을 것)
  • spec.rules / matches: path: {type: PathPrefix, value: /} — 모든 경로(/ 이하 전부)를 이 규칙에 매칭시킴 → /v1/chat/completions, /v1/completions, /v1/completions/render(Phase 5에서 EPP의 token-producer가 호출한 그 엔드포인트) 등 지금까지 호출한 모든 경로가 이 하나의 규칙으로 처리됨
  • backendRefs: kind: InferencePool이라서 매칭된 요청을 일반 Service가 아니라 InferencePool로 포워딩 — 이게 바로 표준 HTTPRoute가 Gateway API Inference Extension과 만나는 지점이다. kind: Service였다면 그냥 k8s 기본 로드밸런싱이었겠지만, kind: InferencePool이라서 Envoy가 EPP ext-proc 스코어링 경로를 타게 된다. weight: 1은 backendRef가 하나뿐이라 의미 없지만(여러 개면 트래픽 비율 분배용), 예를 들어 estimate 모드 EPP와 precise 모드 EPP를 가진 InferencePool 2개를 동시에 두고 카나리 테스트하는 것도 이 필드로 가능하다.
  • timeouts.request: 300s: 요청 타임아웃 300초(LLM 생성이 길어질 수 있어 넉넉하게 설정 — 차트 기본값 httpRoute.requestTimeout)

spec.endpointPickerRef — 가장 중요한 부분: 이 풀의 라우팅 결정을 누가 내리는지를 가리키는 참조: qwen3-router-epp라는 Service의 9002번 포트(gRPC ext-proc 포트). 즉 Envoy Gateway가 이 InferencePool로 오는 요청을 받으면, 직접 파드에 로드밸런싱하는 게 아니라 먼저 qwen3-router-epp:9002에 ext-proc gRPC로 물어봐서 "이 요청을 어떤 파드로 보낼지" 스코어링 결과를 받은 뒤 포워딩한다 — Phase 5~6에서 검증한 precise prefix-cache-aware 라우팅이 바로 이 경로를 통해 동작하는 것이다.

failureMode: FailOpen: 만약 EPP가 응답하지 않거나 다운되면, 라우팅을 차단(FailClose)하지 않고 열어서(FailOpen) 그냥 기본 로드밸런싱(라운드로빈 등)으로 폴백시킨다 → EPP 장애가 곧바로 전체 서비스 장애로 번지지 않도록 하는 안전장치다(llm-d 문서에서 본 FailureMode 스펙의 기본값이자 이 InferencePool CRD에도 명시적으로 박혀 있음).

가장 눈여겨볼 부분: 동점(2, 2). 이번 요청은 두 파드가 완전히 동일한 점수(2점씩)를 받았다. 앞서 Phase 5에서 봤던 "긴 prompt 반복 → 항상 같은 파드로만 감" 케이스와 달리, 이번엔:

  • prefix-cache-scorer: 이 prompt가 어느 파드 캐시에도 안 걸린(신규) prompt라서 두 파드 모두 0점을 받았을 가능성이 높음(가중치 2.0이지만 0 × 2.0 = 0)
  • kv-cache-utilization-scorer + queue-scorer: 두 파드 모두 유휴 상태(직전 vLLM 로그에서 본 Running: 0 reqs)라 둘 다 동일하게 만점(1점씩, 가중치 합 1+1=2)을 받음
  • 결과적으로 0(prefix) + 1(kv-util) + 1(queue) = 2로 양쪽 다 정확히 2점 동점

즉 이 트레이스는 "캐시된 게 없어서 prefix-cache-scorer가 변별력을 못 낸, 순수 load-balancing 상황"을 보여주는 예시다. 이럴 때 max-score-picker는 동점 후보 중 하나를 골라야 하는데, top_endpoints 배열의 첫 번째(vkk2k)가 최종 선택됐을 가능성이 높다(동점 시 결정 규칙은 보통 목록 순서/랜덤).

사실 검증 결과

사실 검증 요청 항목을 실제로 WebFetch/WebSearch로 확인한 결과다.

  1. InferencePool/EPP(Endpoint Picker)의 역할 분담 설명이 llm-d 공식 문서(architecture/core/*) 및 Gateway API Inference Extension(GAIE) 공식 문서와 일치하는지
    → 확인됨(정확함). llm-d EPP 공식 문서를 직접 확인한 결과, EPP를 "llm-d 배포의 '두뇌'"로 정의하고 두 가지 핵심 목표(지능형 라우팅, 공정성/우선순위 관리)를 가진다는 설명, 그리고 6단계 요청 처리 파이프라인(요청 도착→외부 처리→요청 핸들링→플로우 제어→요청 스케줄링→요청 프록시)이 소스 문서 설명과 정확히 일치했다. Gateway API Inference Extension 공식 문서[9]도 확인했는데, EPP를 "Inference Router의 구현체"로, InferencePool을 "특정 모델 서버 프레임워크를 실행하는 엔드포인트들의 집합"으로 정의하며, "llm-d-router를 EPP의 대안적 구현 예시"로 명시적으로 언급하고 있어 llm-d의 EPP가 GAIE 표준의 실제 구현체임이 확인됐다.
  2. EPP Request Scheduler의 파이프라인 순서(Scrapers → Filters → Scorers → Picker)와 각 스코어러(queue-scorer/kv-cache-utilization-scorer/prefix-cache-scorer)의 역할 설명이 정확한지
    → 확인됨, 단 용어 사용에 미세한 차이 있음. llm-d EPP Request Scheduler 공식 문서를 확인한 결과 공식 문서의 정식 파이프라인 명칭은 Filter → Score → Pick 3단계이며, "Scrapers"라는 용어는 EPP 공식 아키텍처 문서(core/router/epp)가 아니라 Red Hat 유튜브 발표(3장)에서 사용된 개념적 설명 용어임을 확인했다. 두 설명은 상충하지 않는다 — "Scrapers"가 실시간 메트릭을 모아오는(수집) 단계를 가리키는 발표자의 비유적 표현이고, 이는 공식 문서의 Data Layer(폴링/수집 계층)가 하는 역할과 대응된다. 즉 발표에서 쓴 4단계(Scrapers/Filters/Scorers/EPP 최종결정)와 공식 문서의 3단계(Filter/Score/Pick) + Data Layer는 서로 다른 프레젠테이션 레벨의 같은 개념이다. queue-scorer(대기열 짧을수록 고점), kv-cache-utilization-scorer(KV 캐시 사용률 낮을수록 고점), prefix-cache-scorer(프리픽스 캐시 일치 길이)의 개별 역할 설명은 공식 문서와 정확히 일치했다.
  3. Envoy ext_proc 필터 및 ORIGINAL_DST 클러스터 타입을 이용한 EPP 라우팅 위임 메커니즘 설명이 Envoy 공식 문서와 부합하는지
    → 확인됨. Envoy Gateway 공식 ext-proc 문서[10]를 확인한 결과, "외부 gRPC 서비스를 호출하여 HTTP 요청과 응답을 가공"한다는 설명이 이 문서의 ext_proc/ORIGINAL_DST 설명과 일치한다. llm-d envoy config 예시 원본 파일도 실제로 확인했고, processing_mode(FULL_DUPLEX_STREAMED), original_destination_cluster(type: ORIGINAL_DST, use_http_header, http_header_name: x-gateway-destination-endpoint) 설정이 소스 문서에 인용된 그대로 원본 파일에 존재함을 확인했다.
  4. llm-d 자체 성능 벤치마크 수치(처리량 최대 3배, 응답속도 2배, 토큰/초 최대 70% 개선)가 llm-d 공식 자료와 일치하는지 (과장 여부 확인)
    → 부분적으로 부정확함(단순화로 인한 오해 소지). llm-d GitHub README를 실제로 확인한 결과, 이 수치들은 하나의 통합된 개선 결과가 아니라 서로 다른 실험 조건별로 따로 측정된 수치임을 확인했다: "3x higher output throughput and 2x faster TTFT with prefix-cache-aware routing vs round-robin"(Llama 3.1 70B, AMD MI300X 기준, prefix-cache 라우팅 조건)과 "Up to 70% higher tokens/sec with prefill/decode disaggregation vs standard vLLM"(P/D 분리 조건)은 서로 다른 기능·다른 벤치마크 조건에서 나온 값이다. 소스 문서(및 llm-d 공식 docs 페이지)는 이를 "처리량 최대 3배, 응답속도 2배, 토큰/초 최대 70% 개선"이라는 하나의 나열형 문장으로 단순화해 제시하는데, 이는 원문 자체가 과장이라기보다 여러 실험 조건의 결과를 하나로 뭉쳐 표현한 것이라 독자가 "한 가지 설정으로 모든 지표가 동시에 개선된다"고 오해할 소지가 있다. 실제로는 기능(prefix-cache-aware routing vs P/D disaggregation)별로 수치와 전제 조건(모델, 하드웨어)이 다르다. (본문 2장의 ⚠️ 콜아웃 참고.)
  5. helm chart/이미지 버전(Envoy Gateway v1.9.1, ai-gateway-helm v1.1.0, GAIE CRD v1.6.1, llm-d-router-endpoint-picker:v0.10.0, MetalLB 0.16.1 등)이 문서에 쓰인 그대로 정확한지
    → 확인됨(모두 실제 존재하는 버전). Envoy Gateway GitHub Releases[19]에서 v1.9.1이 "Latest" 릴리스로 확인됐다(2026-08-28 게시). Envoy Gateway Compatibility Matrix에서 v1.9가 Gateway API v1.6.1과 호환됨을 확인했다 — 이는 GAIE(Gateway API Inference Extension) CRD 버전이 Gateway API 버전과 동일 계열(v1.6.1)임을 뒷받침한다. ai-gateway-helm/ai-gateway-crds-helm v1.1.0은 GitHub Releases[20]에서 "the first minor release on the stable 1.x API"로 확인됐다. llm-d-router-endpoint-picker:v0.10.0은 llm-d GitHub Releases에서 이전 버전(v0.9.0)의 다음 릴리스로 명확히 확인됐다. MetalLB v0.16.1은 공식 릴리스 노트[21]에서 확인됐다. 단, 이 버전들은 각 프로젝트의 릴리스 시점에 따라 계속 갱신되므로 실습 시점에는 더 최신 버전이 있을 수 있다.
  6. kubectl/helm 명령의 옵션과 순서가 문서에 쓰인 그대로 정확한지
    → 확인됨. 원문에 있는 모든 kubectl/helm 명령을 그대로 옮겨 실었으며, 임의로 옵션을 수정하거나 순서를 바꾸지 않았다. 단, Phase 3의 addon 트러블슈팅 재현 커맨드(35장)는 원문에 정확한 명령어 로그가 남아있지 않고 트러블슈팅 서술만 있어, 이 문서에서는 "재현 개념 요약"이라고 명시하고 일반적인 Helm 롤백 패턴(helm rollback)으로 흐름을 구성했다는 점을 밝힌다 — 이는 원문에 없는 내용을 추가한 것이므로 사실 여부가 아니라 "개념 설명 보조"로만 참고해야 한다.
  7. KV 캐시 관련 3가지 기능(Prefix-Cache Aware Routing, KV-Cache Indexer, KV-Cache Offloading)의 구분과 설명이 정확한지
    → 확인됨. llm-d KV Cache Management 공식 문서의 3계층 구조(지능 계층/관찰성 계층/용량 계층) 설명, Prefix-Cache Aware Routing 문서의 근사/정밀 두 방식 구분, KV-Cache Indexer 문서의 Index/Data Producer/Scorer 3요소 구조, KV-Cache Offloading 문서의 네이티브/외부 커넥터 두 방식 구분이 모두 소스 문서 설명과 일치했다. 특히 이 문서 Part B의 Phase 5 실습(정밀 방식의 /v1/completions/render 호출 + ZMQ 이벤트 구독)이 공식 문서의 정밀(Precise) 방식 동작 원리를 실제로 재현하는 것도 확인했다.

    → 확인됨. 이 문서에서 다음 값들을 <YOUR_...> placeholder로 표시했다: <YOUR_GPU_SERVER_IP>(GPU 서버/노드 IP), <YOUR_NODE_NAME>(K3s 노드 이름), <YOUR_METALLB_IP_RANGE_START/END>(MetalLB IP 풀 대역), <YOUR_METALLB_GATEWAY_IP>(Gateway에 할당되는 실제 IP), <YOUR_MINIO_ROOT_USER>/<YOUR_MINIO_ROOT_PASSWORD>(MinIO 자격증명), <YOUR_HF_TOKEN>(HuggingFace 토큰 — 이 실습에서 사용한 Qwen3-0.6B-FP8은 공개 모델이라 실제로는 불필요했음을 원문 그대로 명시), <YOUR_DASHBOARD_JSON_URL_*>(Grafana 대시보드 JSON 다운로드 URL — 원문에 URL이 일부 가려져 있어 실제 값이 무엇인지는 원문에서도 확인 불가능했음), <YOUR_SSH_USER>(결과 파일 scp용 SSH 계정). 네임스페이스(vllm, monitoring, envoy-gateway-system, envoy-ai-gateway-system, metallb-system, nvidia-device-plugin)와 스토리지클래스(local-path)는 원문에 고정값으로 반복 사용되어 사실상 이 실습의 표준 네이밍이므로 placeholder 처리하지 않고 그대로 유지했다.
