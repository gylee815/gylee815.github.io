Envoy 기본 개념
리스너 (Listener)
Envoy가 트래픽을 받기 위해 열어두는 IP/포트. "우편함 투입구"에 해당한다.
루트/라우트 (Route)
리스너로 들어온 트래픽을 어느 클러스터로 보낼지 정하는 규칙. "우편물 분류 규칙"에 해당한다.
클러스터 (Cluster)
Envoy가 트래픽을 라우팅할 수 있는 논리적 백엔드 서비스(엔드포인트 집합). "실제 배달 목적지 그룹"에 해당한다.
업스트림/다운스트림
업스트림은 Envoy가 연결하는 백엔드, 다운스트림은 Envoy에 연결하는 클라이언트를 가리킨다.
필터 체인 (Filter Chain)
리스너로부터 서비스까지 요청이 거쳐가는 처리 파이프라인. "공장의 조립 라인"에 해당한다.
xDS 동적 설정 API
xDS
Envoy를 재시작 없이 실시간으로 재설정하는 API군의 통칭. "실시간 내비게이션"에 해당한다.
LDS (Listener Discovery Service)
Envoy가 어떤 리스너를 노출해야 하는지 알려주는 API.
RDS (Route Discovery Service)
리스너가 사용할 라우트 설정을 알려주는 API (LDS의 부분집합).
CDS (Cluster Discovery Service)
Envoy가 사용할 클러스터 목록과 설정을 알려주는 API.
EDS (Endpoint Discovery Service)
클러스터가 사용할 실제 엔드포인트를 알려주는 API (CDS의 부분집합).
SDS (Secret Discovery Service)
TLS 인증서·키 같은 비밀 정보를 배부하는 API.
ADS (Aggregated Discovery Service)
LDS/RDS/CDS/EDS/SDS의 모든 변경 사항을 하나의 gRPC 스트림으로 순서 보장하며 전달하는 API.
확장 메커니즘
ext_proc (External Processing)
Envoy가 요청/응답 처리를 Envoy 프로세스 밖의 별도 gRPC 서버(External Processor)에 위임하는 필터. "외부 컨설턴트 셰프"에 해당한다.
EnvoyFilter
Istio에서 Envoy의 필터 체인을 직접 커스터마이징할 수 있게 해주는 CRD. 잘못 쓰면 메시 전체를 마비시킬 수 있는 고급 기능이다.
tap 필터
요청/응답을 가로채지 않고 복사해서 콘솔/CLI 등 별도 수신자에게 실시간으로 보여주는 필터. "전화 도청 장치"에 해당한다.
AI Gateway / Agent Router
AI(LLM) Gateway
여러 모델 프로바이더 API를 하나의 통합 API로 묶고 키 관리·재시도/장애조치·토큰 추적·관측성을 제공하는 계층.
Envoy Agent Router (구 Envoy AI Gateway)
Envoy 기반으로 구현된 오픈소스 AI Gateway. 2025년 2월 v0.1로 시작해 2026년 v1.0에서 안정화된 뒤 이름을 Agent Router로 바꾸고 AAIF에 합류했다.
AIGatewayRoute
AI 트래픽의 통합 진입점을 정의하는 CRD. 라우팅 규칙, 요청/응답 변환, 비용 모니터링을 담당한다. "여행사"에 해당한다.
AIServiceBackend
개별 AI 백엔드(OpenAI, Bedrock, mock 등)를 표현하는 CRD. 백엔드가 기대하는 API 스키마를 정의한다. "항공사"에 해당한다.
BackendSecurityPolicy
백엔드 접근 인증(API Key, AWS 자격증명 등)을 설정하는 CRD. "발권 시스템"에 해당한다.
AAIF (Agentic AI Foundation)
"엔터프라이즈 규모에서 에이전틱 AI를 운영화"하는 것을 미션으로 하는 벤더 중립 재단. Agent Router가 대표 프로젝트 중 하나다.
Gateway API Inference Extension
InferencePool
동일한 모델을 서빙하는 Pod들의 집합을 나타내는 K8s CRD. 일반 Service와 달리 EPP가 매 요청마다 최적 Pod를 선택하도록 위임한다.
EPP (Endpoint Picker)
InferencePool 안의 Pod들 중 큐 길이·KV 캐시 상태 등을 기준으로 최적 엔드포인트를 골라주는 컴포넌트. "종합병원 접수/배정 시스템"에 해당한다.
GAIE (Gateway API Inference Extension)
K8s Gateway API를 추론(inference) 트래픽에 특화되도록 확장하는 표준 API. EPP와 BBR을 포함한다.
BBR (Body Based Router)
요청 본문(body)에서 모델명을 추출해 헤더로 주입하는 ext_proc 확장 서비스. Envoy는 헤더만 보고 라우팅하기 때문에 필요하다.
ORIGINAL_DST 클러스터
고정된 엔드포인트 목록 없이 매 요청마다 목적지를 동적으로 결정하는 Envoy 클러스터 타입. EPP가 헤더로 지정한 목적지로 직접 연결한다.

핵심 요약
  1. Envoy는 Lyft가 만든 고성능 L3/L4/L7 프록시로, 리스너·루트·클러스터라는 3대 개념과 xDS(동적 설정) API를 기반으로 서비스 디스커버리·로드밸런싱·재시도·서킷브레이커·관찰성을 제공하며, Istio의 데이터 플레인(사이드카 프록시)으로도 쓰인다.
  2. AI(LLM) Gateway는 여러 모델 프로바이더 API를 하나의 통합 API로 묶고 키 관리·재시도/장애조치·토큰 사용량 추적·관측성을 제공하는 계층으로, Envoy는 ext_proc(External Processing) 필터를 통해 이 AI 특화 로직을 코어 코드 변경 없이 확장한다.
  3. Envoy AI Gateway는 2025년 2월 v0.1로 시작해 2026년 v1.0에서 안정화되었고, 이후 Envoy Agent Router로 이름을 바꿔 Agentic AI Foundation(AAIF)에 합류했다. 이 문서 Part C에서는 kind K8s + Envoy Gateway + Agent Router를 직접 설치하고, mock 백엔드·실제 OpenAI 연동·Gateway API Inference Extension(EPP)을 이용한 멀티모델(Llama/Qwen) 라우팅까지 전부 손으로 실습한다.

Agent Router Controller가 AI 관련 CRD 변화를 감지해 Envoy Gateway Controller에게 "이 xDS 설정을 이렇게 미세조정해달라"고 전달하고(Extension Server 훅), Envoy Gateway Controller는 이를 표준 xDS(ADS/DELTA_GRPC)로 데이터 플레인 파드에 스트리밍한다. 데이터 플레인 파드 안에서는 Envoy Proxy와 AI Gateway ExtProc가 Unix Domain Socket으로 통신하며 실제 모델 라우팅·토큰 계측·포맷 변환을 수행한다.

Part A. Envoy Proxy 기초

이 파트는 소스 문서 1~1615줄 근처의 "Istio Study 참고 자료"를 기반으로 하며, 원문은 『Istio in Action』(에이콘출판, Acorn Publishing) 3장·14장 내용을 저자가 실습하며 정리한 것이다.

1. Envoy란 무엇인가

💡
비유로 이해하기: Envoy는 아파트 단지의 "경비실 겸 안내 데스크"라고 생각하면 된다. 방문객(클라이언트)이 특정 세대(서비스 인스턴스)를 직접 찾아가지 않고 경비실에 문의하면, 경비실이 어느 세대가 비었는지·바쁜지 파악해서 안내해주고, 문제가 생기면 대신 처리해준다.
  • Envoy는 분산 시스템을 구축할 때 발생하는 어려운 애플리케이션 네트워킹 문제를 해결하고자 Lyft가 개발했다.
  • 2016년 9월 오픈소스로 공개되었고, 1년 후인 2017년 9월 CNCF에 합류했다.
  • C++로 작성되었으며, 목표는 성능을 높이고 높은 부하에서도 안정적이고 결정론적으로 동작하는 것이다.
  • 두 가지 핵심 설계 원칙:

    "The network should be transparent to applications. When network and application problems do occur it should be easy to determine the source of the problem." — Envoy announcement

참고 자료: Envoy 공식 - Life of a Request[1] 문서를 열어보면 요청이 리스너 → (TLS 종료) → 네트워크 필터 체인(HTTP Connection Manager) → HTTP 필터 체인(라우터 필터로 종료) → 클러스터의 로드밸런싱 → 업스트림 HTTP 필터 체인 순으로 처리되고, 응답은 반대 순서로 흐른다는 12단계 Request Flow가 그대로 나와 있다.

2. Envoy 핵심 개념: 리스너 · 루트 · 클러스터

프록시란 클라이언트와 서버 간 통신의 중간에 위치한 중개 구성 요소다. 프록시가 중간에 위치함으로써 보안, 프라이버시, 정책 같은 기능을 추가할 수 있다.

클라이언트가 서비스 인스턴스의 배포 방식을 몰라도, 프록시가 로드밸런싱과 헬스체크를 대신 처리해준다.

Envoy 고수준 개념 (비유: "우체국 시스템"):

  • 리스너(Listener) — 우체국의 "우편함 투입구". 애플리케이션이 연결할 수 있도록 외부 세계로 포트를 노출한다. 예: 포트 80 리스너는 트래픽을 받고 설정된 동작을 적용한다.
  • 루트/라우트(Route) — "우편물 분류 규칙". 리스너로 들어온 트래픽을 어디로 보낼지 정하는 규칙. 예: /catalog로 시작하는 요청은 catalog 클러스터로 보낸다.
  • 클러스터(Cluster) — "실제 배달 목적지 그룹". Envoy가 트래픽을 라우팅할 수 있는 특정 업스트림 서비스. 예: catalog-v1과 catalog-v2는 별도 클러스터일 수 있고, 루트가 v1/v2 중 어디로 보낼지 정한다.

트래픽은 다운스트림 시스템에서 리스너로 들어오고, 클러스터를 거쳐 업스트림 시스템으로 나간다.

용어 추가 정리 (Envoy 공식 용어집 - Docs[2] 확인):

  • Cluster: Envoy가 트래픽을 포워드할 수 있는 논리적인 서비스(엔드포인트 세트)
  • Endpoint: IP 주소, 네트워크 노드로 클러스터로 그룹핑되는 실제 접근 가능한 지점
  • Filter: 리스너로부터 서비스에 트래픽을 전달하기까지의 요청 처리 파이프라인
  • Upstream: Envoy가 요청을 포워딩해서 연결하는 백엔드
  • Downstream: Envoy에 연결하는 엔티티(클라이언트)

참고 이미지 (정환열님이 작성해 공유한 Istio 사내 교육 자료): 아래 두 이미지는 지금까지 설명한 리스너·루트·클러스터·필터·업스트림/다운스트림 용어를 한 장으로 정리한 자료다.

3. Envoy 확장하기 & 다른 프록시와 비교

Envoy의 핵심은 프로토콜(7계층) 코덱(필터)을 구축할 수 있는 바이트 처리 엔진이다. 필터는 C++로 작성돼 Envoy 바이너리로 컴파일되지만, Lua 스크립트와 WebAssembly(Wasm)로도 덜 침습적인 방식으로 확장할 수 있다.

Envoy가 다른 프록시보다 뛰어난 영역: - 웹어셈블리를 통한 확장성 - 공개 커뮤니티 - 유지보수/확장이 용이한 모듈식 코드베이스 - HTTP/2 지원(업스트림·다운스트림 모두) - 심층 프로토콜 메트릭 수집 - C++/가비지 컬렉션 없음 - 동적 설정으로 핫 리스타트 불필요

참고: Envoy vs 다른 프록시 비교, Turbine Labs의 Nginx→Envoy 전환

4. Envoy 설정: 정적(Static) vs 동적(Dynamic)

Envoy는 JSON/YAML 형식 설정 파일로 구동된다. 이 책에서는 v3 설정만 다룬다(v1, v2는 deprecated, v3는 최신이자 Istio가 사용).

4.1 정적(Static) 설정 예시

static_resources:
  listeners: # (1) 리스너 정의
  - name: httpbin-demo
    address:
      socket_address: { address: 0.0.0.0, port_value: 15001 }
    filter_chains:
    - filters:
      - name:  envoy.filters.network.http_connection_manager # (2) HTTP 필터
        typed_config:
          "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
          stat_prefix: ingress_http
          http_filters:
          - name: envoy.filters.http.router
          route_config: # (3) 라우팅 규칙
            name: httpbin_local_route
            virtual_hosts:
            - name: httpbin_local_service
              domains: ["*"] # (4) 와일드카드 가상 호스트
              routes:
              - match: { prefix: "/" }
                route:
                  auto_host_rewrite: true
                  cluster: httpbin_service # (5) 클러스터로 라우팅
  clusters:
    - name: httpbin_service # (6) 업스트림 클러스터
      connect_timeout: 5s
      type: LOGICAL_DNS
      dns_lookup_family: V4_ONLY
      lb_policy: ROUND_ROBIN
      load_assignment:
        cluster_name: httpbin
        endpoints:
        - lb_endpoints:
          - endpoint:
              address:
                socket_address:
                  address: httpbin
                  port_value: 8000

이 설정은 15001 포트에 소켓을 열고, 모든 트래픽(domains: ["*"], prefix: "/")을 httpbin_service 클러스터로 라우팅한다. 업스트림 서비스 디스커버리는 LOGICAL_DNS, 로드밸런싱은 ROUND_ROBIN을 사용한다. - Docs

4.2 동적(Dynamic) 설정: xDS API

Envoy는 다운타임이나 재시작 없이 실시간으로 설정을 업데이트할 수 있는 API군을 사용한다. 이를 통칭해 xDS 서비스라고 부른다. (비유: "실시간 내비게이션". 정적 설정은 종이 지도, xDS는 실시간 교통정보를 반영하는 내비게이션 앱과 같다.)

API 정식 이름 역할
LDS Listener Discovery Service Envoy가 어떤 리스너를 노출해야 하는지 쿼리하는 API
RDS Route Discovery Service 리스너 설정의 일부로 사용할 루트를 지정 (LDS의 부분집합)
CDS Cluster Discovery Service Envoy가 클러스터 목록과 각 클러스터 설정을 찾는 API
EDS Endpoint Discovery Service 클러스터가 사용할 엔드포인트 지정 (CDS의 부분집합)
SDS Secret Discovery Service 인증서를 배부하는 데 사용하는 API
ADS Aggregated Discovery Service 나머지 API의 모든 변경 사항을 하나의 직렬화된 스트림으로 제공

xDS API는 궁극적 일관성(eventual consistency)을 전제로 구축되었다.

Service Mesh 솔루션이나 Gateway API 구현체들은 대부분 Envoy를 내부적으로 사용하며, Envoy가 제공하는 이 동적 구성 API(xDS Sync API)를 이용해 다양한 네트워크 정책을 구성한다. 예를 들어 새 루트가 RDS로 클러스터 foo를 가리키도록 업데이트됐는데 CDS가 아직 foo를 반영하지 않았다면, 그 사이에 라우팅 오류가 발생할 수 있다. 이런 순서 경쟁 상태(race condition)를 해결하기 위해 ADS가 도입됐고, Istio는 프록시 설정 변경에 ADS를 구현한다.

동적 리스너 설정 예시:

dynamic_resources:
  lds_config: # Configuration for listeners (LDS) 리스너용 설정
    api_config_source:
      api_type: GRPC
      grpc_services:
        - envoy_grpc: # Go to this cluster for the listener API. 이 클러스터로 이동해 리스너 API를 확인하자
            cluster_name: xds_cluster

clusters:
- name: xds_cluster # gRPC cluster that implements LDS. LDS를 구현하는 gRPC 클러스터
  connect_timeout: 0.25s
  type: STATIC
  lb_policy: ROUND_ROBIN
  http2_protocol_options: {}
  hosts: [{ socket_address: {
    address: 127.0.0.3, port_value: 5678 }}]

Istio가 서비스 프록시용으로 사용하는 부트스트랩 설정 예시(ADS 사용):

bootstrap:
  dynamicResources:
    ldsConfig:
      ads: {} # ADS for listeners 리스너용 ADS
    cdsConfig:
      ads: {} # ADS for clusters 클러스터용 ADS
    adsConfig:
      apiType: GRPC
      grpcServices:
      - envoyGrpc:
          clusterName: xds-grpc # Uses a cluster named xds-grpc 라는 클러스터를 사용
      refreshDelay: 1.000s

  staticResources:
    clusters:
    - name: xds-grpc # Defines the xds-grpc cluster 라는 클러스터를 정의
      type: STRICT_DNS
      connectTimeout: 10.000s
      hosts:
      - socketAddress:
          address: istio-pilot.istio-system
          portValue: 15010
      circuitBreakers: # Reliability and circuit-breaking settings 신뢰성 및 서킷 브레이커 설정
        thresholds:
        - maxConnections: 100000
          maxPendingRequests: 100000
          maxRequests: 100000
        - priority: HIGH
          maxConnections: 100000
          maxPendingRequests: 100000
          maxRequests: 100000
      http2ProtocolOptions: {}

참고 자료: Envoy 공식 xDS Protocol 문서[3]에도 같은 내용이 나온다. LDS/CDS는 Envoy 인스턴스당 항상 wildcard로 구독되고, Envoy는 시작 시 모든 Listener/Cluster를 먼저 가져온 뒤 필요한 RouteConfiguration과 ClusterLoadAssignment를 순차적으로 가져온다. ADS는 "a single management server, via a single gRPC stream"이라는 표현대로, 여러 리소스 타입을 하나의 gRPC 스트림에 멀티플렉싱한다.

8. Envoy가 Istio에 어떻게 들어맞는가

Envoy는 Istio가 다루는 기능 대부분에서 핵심 역할을 맡는 프록시지만, 최대한 활용하려면 보조 인프라(컨트롤 플레인)가 필요하다.

istiod는 Kubernetes API를 사용해 VirtualService 등의 Istio 설정을 읽은 다음, xDS API로 서비스 프록시를 동적으로 설정한다. Istio를 Kubernetes에 배포하면 서비스 디스커버리에 Kubernetes의 서비스 저장소를 사용하며, 이 구현 세부사항은 Envoy 프록시에게 완전히 감춰진다.

Envoy는 트레이스 스팬을 오픈트레이싱 엔진(예: Jaeger, Zipkin)에 보낼 수 있고, Istio가 이 연동을 설정한다.

Envoy는 메시 내 서비스로 향하는 TLS 트래픽을 종료/시작할 수 있으며, 인증서 생성·서명·로테이션은 istiod가 담당한다.

Summary: - Envoy는 애플리케이션 수준 동작에 사용할 수 있는 프록시다. - Envoy는 Istio의 데이터 플레인이다. - Envoy는 클라우드 신뢰성 문제(네트워크 장애, 토폴로지 변경, 탄력성)를 일관되고 정확하게 해결한다. - Envoy는 런타임 제어를 위해 동적 API를 사용한다(Istio가 이를 사용). - Envoy는 애플리케이션 사용 및 프록시 내부에 대한 강력한 지표를 노출한다.

9. Envoy Life of a Request (공식 문서 심화)

참고 자료: Envoy 공식 - Life of a Request가 설명하는 Request Flow 12단계를 정리하면 다음과 같다.

  1. 다운스트림 TCP 연결이 워커 스레드에서 실행되는 리스너에 의해 수락됨
  2. 리스너 필터 체인 실행(SNI 등 pre-TLS 정보 제공) → 네트워크 필터 체인 매칭
  3. TLS 트랜스포트 소켓이 데이터를 복호화
  4. 네트워크 필터 체인 실행 — 가장 중요한 것이 HTTP Connection Manager(HCM), 항상 체인의 마지막
  5. HCM의 HTTP/2 코덱이 스트림을 디프레임/디멀티플렉싱
  6. 각 스트림마다 다운스트림 HTTP 필터 체인 실행 → 라우터 필터에서 라우트/클러스터 결정
  7. 클러스터별 로드밸런싱으로 엔드포인트 결정, 서킷 브레이커 체크
  8. 각 스트림마다 업스트림 HTTP 필터 체인 실행(기본은 CodecFilter만)
  9. 업스트림 커넥션의 HTTP/2 코덱이 스트림을 멀티플렉싱
  10. 업스트림 TLS 트랜스포트 소켓이 암호화 후 전송
  11. 요청/응답이 프록시되며, 응답은 반대 순서로 필터를 통과
  12. independent half-close 활성화 시 양방향 END_STREAM + 2xx 응답 후 스트림 파괴, 아니면 응답 완료 시 파괴

10. 엔보이 필터 체인 이해하기 (14장)

💡
비유로 이해하기: 필터 체인은 "공장의 조립 라인"과 같다. 원재료(바이트 스트림)가 여러 작업대(필터)를 순서대로 거치며 가공되어 최종 제품(HTTP 요청/응답)이 된다.
  • 리스너는 네트워킹 인터페이스에 포트를 열고 들어오는 트래픽 수신을 시작하는 방법이다.
  • Envoy는 궁극적으로 네트워크 커넥션에서 바이트를 가져와 처리하는 L3/L4 프록시다.

Envoy의 가장 기본적인 필터는 네트워크 필터로, 바이트 스트림에서 인코딩/디코딩 작업을 한다. 대표 네트워크 필터: MongoDB, Redis, Thrift, Kafka, HTTP Connection Manager(HCM).

가장 많이 쓰이는 네트워크 필터는 HttpConnectionManager이다. 이 필터는 바이트 스트림을 HTTP 헤더/바디/트레일러로 변환하는 세부사항을 추상화한다.

HCM은 필터 기반 아키텍처를 갖고 있어 HTTP 필터를 체인으로 구성할 수 있다. 기본 HTTP 필터 예시 - 전체 목록[4]: CORS, CSRF, ExternalAuth, RateLimit, Fault injection, gRPC/JSON transcoding, Gzip, Lua, RBAC, Tap, Router, WebAssembly(Wasm).

HTTP 필터는 반드시 업스트림 클러스터로 요청을 보내는 터미널 필터로 끝나야 하며, 이를 담당하는 것이 라우터 필터다. - Docs

사용자는 Envoy 핵심 코드를 변경하지 않고도 자신만의 필터를 작성해 프록시 위에 계층화할 수 있다(예: Istio 프록시는 데이터 플레인용으로 Envoy 위에 필터를 추가해 커스텀 Envoy를 빌드한다). 다만 이는 유지보수 부담이 크고 C++가 필요하다.

11.4 tap 필터 실습

💡
비유로 이해하기: tap 필터는 "전화 도청 장치"와 같다. 실제 통화(요청/응답)에는 영향을 주지 않으면서, 지나가는 내용을 복사해 별도의 수신자(콘솔/CLI)에게 실시간으로 보여준다.

이스티오의 데이터 플레인을 확장하는 첫 단계는 엔보이의 기존 필터가 충분한지 파악하는 것이다. 이 예제에서는 webapp 워크로드를 지나는 메시지를 샘플링하도록 tap 필터를 설정한다.

EnvoyFilter 리소스 적용 전 3가지 유의사항: 1. 달리 지정하지 않으면 네임스페이스의 모든 워크로드에 적용됨 (workloadSelector로 특정 가능) 2. 다른 Istio 리소스가 모두 변환/설정된 후에 적용됨 3. 잘못 설정하면 메시 전체를 마비시킬 수 있는 고급 사용법("break glass" 솔루션)

EnvoyFilter 리소스(ch14/tap-envoy-filter.yaml):

apiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: tap-filter
  namespace: istioinaction
spec:
  workloadSelector:
    labels:
      app: webapp # 워크로드 셀렉터
  configPatches:
  - applyTo: HTTP_FILTER # 설정할 위치
    match:
      context: SIDECAR_INBOUND
      listener:
        portNumber: 8080
        filterChain:
          filter:
            name: "envoy.filters.network.http_connection_manager"
            subFilter:
              name: "envoy.filters.http.router"
    patch: # 엔보이 설정 패치
      operation: INSERT_BEFORE
      value:
       name: envoy.filters.http.tap
       typed_config:
          "@type": "type.googleapis.com/envoy.extensions.filters.http.tap.v3.Tap"
          commonConfig:
            adminConfig:
              configId: tap_config

설명: (1) workloadSelector로 webapp 워크로드에만 적용, (2) 8080 포트 리스너의 인바운드(SIDECAR_INBOUND) HTTP_FILTER 중 envoy.filters.http.router 앞에 패치할 위치 지정, (3) INSERT_BEFORE로 tap 필터를 router 필터 바로 앞에 삽입.

12. [실습] 외부 호출로 요청 속도 제한하기 (Rate Limiting)

💡
비유로 이해하기: 전역 속도 제한은 "놀이공원 입장 카운터"와 같다. 여러 매표소(Envoy 프록시 복제본)가 있어도, 모두 같은 중앙 카운터(속도 제한 서버 + 백엔드 저장소)에 입장 인원을 보고하기 때문에 전체 놀이공원 정원을 정확히 지킬 수 있다.

Istio 데이터 플레인에서 속도 제한 호출은 Envoy HTTP 필터에서 나온다. Envoy에는 네트워크 필터/로컬/글로벌 속도 제한이 있는데, 여기서는 글로벌 속도 제한을 살펴본다. 글로벌 속도 제한은 특정 워크로드의 모든 Envoy 프록시가 동일한 속도 제한 서비스를 호출하며, 이 서비스는 백엔드 글로벌 키-값 저장소를 호출한다.

속도 제한을 하려면 Envoy 커뮤니티의 속도 제한 서버를 배포하거나 Envoy 속도 제한 API를 구현하는 서버를 배포해야 한다. 이 서버는 백엔드 Redis 캐시와 통신하며 속도 제한 카운터를 저장한다(Memcached도 가능).

12.1 엔보이 속도 제한 이해하기

속도 제한 필터는 요청 처리 시 특정 속성을 가져와 RLS로 보내 평가받는다. 이 속성(또는 속성 그룹)을 디스크립터라고 부른다.

12.2 엔보이 속도 제한 서버 설정하기

로열티 등급별 제한: 골드(x-loyalty: gold) 분당 10개, 실버(x-loyalty: silver) 분당 5개, 브론즈(x-loyalty: bronze) 분당 3개, 식별 불가 시 분당 1개.

kind: EnvoyFilter
metadata:
  name: catalog-ratelimit-actions
  namespace: istioinaction
spec:
  workloadSelector:
    labels:
      app: catalog

        context: SIDECAR_INBOUND
        routeConfiguration:
          vhost:
            route:
              action: ANY
      patch:
        operation: MERGE
        # Applies the rate limit rules.
        value:
          rate_limits: # 속도 제한 조치
            - actions:

                  descriptor_value: no_loyalty
                  expect_match: false
                  headers:
                  - name: "x-loyalty"
            - actions:
              - header_value_match:
                  descriptor_value: bronze_request
                  headers:
                  - name: "x-loyalty"
                    exact_match: bronze
            - actions:
              - header_value_match:
                  descriptor_value: silver_request
                  headers:
                  - name: "x-loyalty"
                    exact_match: silver

Part B. AI Gateway 개념 — Envoy AI Gateway에서 Agent Router로

13. AI(LLM) Gateway가 왜 필요한가

참고 자료: AI Gateway: The Layer Every AI Stack Eventually Needs (Devsplainers)[17] — 2026-07-08 게시. 이 영상의 핵심은 이렇다. AI Gateway(=LLM Gateway)는 애플리케이션과 OpenAI/Anthropic/Google 등 모델 프로바이더 사이에 있는 "공유 계층"으로, 개별 서비스가 각자 API 키를 들고 재시도 로직을 짜는 대신 (1) 프로바이더 전체에 걸친 단일 통합 API, (2) 키 관리, (3) 자동 재시도·장애조치, (4) 토큰/비용 추적, (5) 관측성을 한곳에 모은다. 다만 영상은 "모든 트래픽이 게이트웨이 하나를 통과하므로 그 자체가 단일 장애점(SPOF)이 될 수 있다"는 트레이드오프도 명확히 짚는다 — 그래서 백업 경로와, 게이트웨이를 건너뛰고 직접 프로바이더를 호출할 수 있는 코드 경로를 함께 준비해야 한다고 강조한다.

배경(문제 상황):

첫 번째 AI 모델 제공 업체를 쓰다가 용량 제한에 걸리면 다른 모델 제공 업체를 쓰게 된다.

2명 이상의 팀원이 여러 모델 제공업체를 사용하면, 키 정보를 복사하기도 하고 재시도 로직을 매번 새로 작성해야 한다.

청구서에서 비용을 분석하기 어려워진다.

약 3개월 후에는 모든 팀원이 같은 문제(Auth, Retry, Keys, Logs를 각자 구현)를 겪게 된다.

만약 모델 제공업체 1곳이 장애가 나면 제품 구현 전체에 영향을 미친다.

10년 전에 이미 다수의 백엔드에 대한 공통 로직이 필요해 API Gateway 제품이 나왔다.

AI Gateway도 같은 개념이며, 대상만 "백엔드"에서 "모델"로 바뀐 것이다. (비유: 전통 API Gateway가 여러 마이크로서비스를 위한 "공동 현관"이었다면, AI Gateway는 여러 LLM 프로바이더를 위한 "공동 현관"이다.)

14. AI Gateway의 5가지 역할

참고 자료: Envoy AI Gateway Reference Architecture 블로그 — Two-Tier Gateway Design(외부용/내부용 게이트웨이 분리)과 KServe를 이용한 Self-Hosted Model Serving 아키텍처를 다룬다.

  1. Unified API — 모든 모델(프로바이더)과 통신할 수 있는 통합 API. 프로바이더별로 요청 형식(재시도 등)이 다른데, 대부분 OpenAI 방식을 따르므로 모델명만 바꿔서 다른 프로바이더 모델을 사용할 수 있다.
  1. Holds the Keys — AI GW가 제공업체의 키를 보관하고, 각 앱에는 1회용 키(실제 키와 매핑되는 키)를 제공한다. 일회용 키를 교체/취소해도 다른 앱들은 영향받지 않는다.
  1. Retry & Failover — 모델 문제 시 재시도·장애 조치를 제공한다.
  1. Track Everything — 토큰 전달 과정을 추적해 예산을 관리한다.
  1. Observability + Guard Rails — 모든 트래픽이 AI GW를 통과하므로 한 곳에서 지연시간·오류·지출비용을 모니터링할 수 있다. 이를 위해서는 우회 경로 차단이 필수다.

16. Envoy External Processing (ext_proc) — AI 로직이 Envoy 코어에 침투하지 않는다

💡
비유로 이해하기: ext_proc는 "레스토랑의 외부 컨설턴트 셰프"와 같다. 주방(Envoy 코어) 자체를 새로 리모델링하지 않고도, 매 요리(요청/응답)가 나갈 때마다 외부 셰프에게 전화를 걸어 "이 요리 간을 좀 봐줘, 필요하면 조미료를 추가해줘"라고 요청하는 것이다.

개념:

Envoy가 요청/응답을 처리하는 도중, 그 처리 로직을 Envoy 프로세스 밖의 별도 gRPC 서버(External Processor)에 위임하는 필터(envoy.filters.http.ext_proc)다. Envoy 자체에 커스텀 필터를 C++로 만들어 넣는 대신, 어떤 언어로든 gRPC 서비스만 구현하면 트래픽을 가로채 조작할 수 있다.

동작 방식:

Envoy가 HTTP 요청/응답 라이프사이클의 각 단계(RequestHeaders → RequestBody → ResponseHeaders → ResponseBody)마다 외부 프로세서에게 gRPC 스트림으로 데이터를 보낸다. 외부 프로세서는 CONTINUE(그대로 통과), 수정(헤더/바디 변경), 즉시 응답 반환(예: 401 차단) 중 하나로 응답한다. processing_mode 설정으로 어느 단계까지 개입할지 세밀하게 제어할 수 있다.

주요 용도: 인증/인가(커스텀 토큰 검증), 요청/응답 변환(헤더 삽입, 바디 rewrite), 요청 기반 라우팅 결정, 콘텐츠 검사/차단(모더레이션, PII 마스킹). LLM/AI Gateway 시나리오에서는 Envoy AI Gateway, kgateway 같은 프로젝트가 ext_proc를 이용해 OpenAI 호환 요청 본문을 파싱 → 모델명 기반 라우팅, 토큰 카운트 기반 rate limiting, 프롬프트 가드레일, 사용량 계측(usage metering) 등을 구현한다.

참고: gRPC이므로 매 요청마다 네트워크 왕복(hop)이 추가되어 레이턴시 오버헤드가 있다. 실무에선 sidecar가 아니라 Envoy Gateway/Istio 등이 관리하는 gateway 레벨에 붙이는 경우가 많다.

참고 자료: Envoy Gateway 공식 ext-proc 문서[5]에도 같은 방식이 나온다. EnvoyExtensionPolicy CRD로 특정 Gateway/HTTPRoute에 연결하며, processingMode 필드로 헤더/바디 중 무엇을 외부 프로세서로 보낼지 선택적으로 지정한다(기본값은 아무것도 보내지 않음).

16.1 (참고) llm-d envoy config 예시 — Github[16]

클라이언트 → Envoy(:8081) → [ext_proc gRPC 호출: 어느 파드로 보낼지 결정] → 결정된 파드로 직접 프록시. 일반적인 K8s Service(L4, 연결 단위 로드밸런싱)와 달리, 매 요청마다 외부 프로세스(EPP)가 판단해서 목적지를 동적으로 지정하는 L7 라우팅이다.

http_filters 핵심: ext_proc

http_filters:
  - name: envoy.filters.http.ext_proc
    typed_config:
      "@type": type.googleapis.com/envoy.extensions.filters.http.ext_proc.v3.ExternalProcessor
      grpc_service:
        envoy_grpc:
          cluster_name: ext_proc
          authority: localhost:9002
        timeout: 10s
      processing_mode:
        request_header_mode: SEND
        response_header_mode: SEND
        request_body_mode: FULL_DUPLEX_STREAMED
        response_body_mode: FULL_DUPLEX_STREAMED
        request_trailer_mode: SEND
        response_trailer_mode: SEND
      message_timeout: 1000s
  • 모든 요청/응답 헤더를 EPP(localhost:9002, gRPC)에 전달(SEND)
  • 요청/응답 바디는 FULL_DUPLEX_STREAMED: 버퍼링 없이 스트리밍 중에도 양방향으로 실시간 전달. vLLM의 SSE 스트리밍 응답을 토큰 단위로 그대로 통과시키면서 EPP가 관찰할 수 있게 함(전체 응답을 기다렸다 처리하면 스트리밍 UX가 깨짐)
  • message_timeout: 1000s: EPP 응답을 최대 1000초까지 기다림(긴 생성 스트림 처리 고려)
  • EPP(External Processor)가 하는 일: 요청 헤더(모델명 등)를 보고 llm-d의 스케줄러 로직으로 "이 요청을 어느 vLLM 파드로 보낼지" 결정한다. 실제 llm-d는 각 파드의 KV 캐시 히트율, 큐 길이, GPU 사용률 같은 실시간 서빙 상태를 반영해서 결정한다(kube-proxy처럼 "어느 파드가 바쁜지 전혀 모르고 무작위로 연결하는" 방식과 정반대).

original_destination_cluster 핵심 트릭:

- name: original_destination_cluster
  type: ORIGINAL_DST
  lb_policy: CLUSTER_PROVIDED
  original_dst_lb_config:
    use_http_header: true
    http_header_name: x-gateway-destination-endpoint
  • type: ORIGINAL_DST는 Envoy의 특수 클러스터 타입으로, 고정된 엔드포인트 목록이 없고 매 요청마다 목적지를 동적으로 결정한다.
  • use_http_header: true + http_header_name: x-gateway-destination-endpoint: EPP가(ext_proc 단계에서) 요청 헤더에 x-gateway-destination-endpoint: <파드IP>:<포트>를 심어주면, Envoy는 그 헤더 값 그대로 해당 파드에 직접 연결한다.
  • 즉 로드밸런싱 결정을 Envoy의 표준 알고리즘(round-robin, least-request 등)이 아니라 EPP가 매 요청 단위로 100% 위임받아 내린다 → kube-proxy의 "연결 단위 무작위 배정 후 keep-alive로 고착" 문제가 구조적으로 발생할 수 없다(요청마다 헤더로 새로 지정하므로). 보안 주의: 이 방식은 클라이언트가 아니라 신뢰할 수 있는 EPP만 x-gateway-destination-endpoint 헤더를 설정할 수 있어야 한다는 전제가 깔려 있다 — 이 헤더가 외부에서 임의로 주입 가능하다면 요청을 임의의 목적지로 우회시킬 수 있으므로, 실제 배포에서는 EPP 앞단(ext_proc 경계)에서 해당 헤더를 반드시 재작성/검증해야 한다.
  • circuit_breakers.max_connections: 40000 등 매우 높은 값: 대량의 동시 스트리밍 연결(긴 LLM 응답들이 오래 열려있음)을 견디도록 사실상 제한을 해제한다.

ext_proc 클러스터 (EPP 자체로 가는 경로):

- name: ext_proc
  type: STATIC
  lb_policy: LEAST_REQUEST
  health_checks:
    - grpc_health_check: {service_name: "envoy.service.ext_proc.v3.ExternalProcessor"}
  load_assignment:
    endpoints: [{address: 127.0.0.1, port_value: 9002}]

EPP가 Envoy와 같은 호스트에 사이드카처럼 동거(127.0.0.1:9002)한다. 원본 파일 상단 주석에도 "Envoy and the EPP are colocated on the same host"라고 명시되어 있으며, 이 no-k8s 버전에선 TLS도 생략(같은 머신 내부 통신)한다. 표준 gRPC 헬스체크로 EPP 생존 여부를 지속 확인한다.

19.1 System Architecture Overview

Control Plane(AI GW Ctrl, Envoy GW Ctrl), Data Plane(Ext Proc, Rate Limit, Envoy Proxy)로 구성된다.

AI Gateway Controller(AI 전용 관심사) vs Envoy Gateway Controller(일반 게이트웨이 관심사):

항목 AI Gateway Controller Envoy Gateway Controller
주 역할 AI 특화 설정 담당 코어 프록시 인프라 설정 담당
설정 대상 External Processor 설정 + Extension Server 메커니즘을 통한 xDS 설정 미세조정 Envoy Proxy(xDS 통해) + Rate Limit Service 설정

19.2 Control Plane 상세 (Agent Router Ctrl, Envoy GW Ctrl)

설정 흐름 (CRD → 데이터 플레인) 5단계: 1. Agent Router Controller가 AI Gateway Custom Resource 변경 감시 2. 이에 대응하는 Envoy Gateway 설정 및 HTTPRoute 리소스 생성 3. Envoy Gateway가 이를 xDS 설정으로 변환 4. Agent Router Controller가 Extension Server 프로토콜을 통해 이 xDS 설정을 다시 미세조정 5. Envoy Proxy가 최종 설정을 받아 트래픽에 적용

데이터 플레인과의 연동: ExtProc 사이드카는 Unix Domain Socket을 통해 Envoy Proxy와 로컬 통신 → 성능 이점 + 세션 어피니티 확보(라우터~업스트림 단계 전반의 프로바이더 fallback 로직에 중요). 관리 대상 리소스: HTTPRoute, HTTPRouteFilter, ExtProc secrets, backend security policy 등 — per-model 우선순위와 프로바이더 fallback을 오케스트레이션한다.

19.3 Data Plane and Traffic Flow

구성요소: - Envoy Proxy: 기본 트래픽 핸들러, AI 특화 서비스들과 연동하는 기반 - AI Gateway External Processor: 요청 라우팅(모델 선택·검증), 응답에서 토큰 사용량 추적, 프로바이더 간 요청/응답 포맷 변환(OpenAI, AWS Bedrock 등) - Rate Limit Service: 토큰 기반 레이트리밋 — 사용량 모니터링 및 레이트리밋 예산 관리

트래픽 흐름: - 요청(Request) 경로: 경로/헤더/모델명 기반 라우팅 → 프로바이더 요구사항에 맞게 요청 변환 → 프로바이더별 인증 적용 → 레이트리밋 정책 검증 - 응답(Response) 경로: 프로바이더 응답을 공통 포맷으로 변환 → 토큰 사용량 추출 → 레이트리밋 집행용 사용량 메트릭 저장

핵심 설계: External Processor는 router 단계와 upstream 단계 두 레벨에서 동작한다. 이 분리 덕분에 한 프로바이더 요청 실패 시 다른 프로바이더로 재시도/폴백할 때, router 단계 재평가 없이 upstream 단계에서만 변환·인증을 다시 적용하면 된다 — 폴백 처리를 깔끔하게 한다. 전체 철학은 "Envoy 코어 코드를 수정하지 않고, 검증된 확장 포인트(ext-proc 등)만으로 AI 특화 로직을 구현"하는 것이다.

19.4 3개 핵심 CRD (AIGatewayRoute, AIServiceBackend, BackendSecurityPolicy)

💡
비유로 이해하기: 이 3개 CRD의 관계는 "여행사 - 항공사 - 발권 시스템"과 비슷하다. 여행사(AIGatewayRoute)가 손님 요청을 받아 어느 항공사(AIServiceBackend)로 보낼지 정하고, 항공사에 발권하려면 특정 결제 시스템(BackendSecurityPolicy)을 통해 인증해야 한다.
  • AIGatewayRoute: AI 트래픽을 위한 통합 API 및 라우팅 규칙 정의 — 진입점 역할. 입력 스키마 지정, 라우팅 로직, 요청/응답 변환, LLM 비용 모니터링 포함
  • AIServiceBackend: 개별 AI 서비스 백엔드 표현 — 백엔드가 기대하는 출력 API 스키마 정의, K8s Service 또는 Envoy Gateway Backend 참조, 인증 정책 연결 가능
  • BackendSecurityPolicy: 백엔드 접근 인증 설정 — API Key, AWS 자격증명 등의 인증 방식 지원
Client Request
     ↓
AIGatewayRoute (통합 진입점 — 라우팅/변환/비용 모니터링)
     ↓
AIServiceBackend (개별 백엔드 — 출력 스키마 정의)
     ↓ (선택적으로 참조)
BackendSecurityPolicy (인증 — API Key / AWS credentials)

핵심: AIGatewayRoute가 중앙 오케스트레이터로서 클라이언트 요청을 받아 적절한 AIServiceBackend로 트래픽을 분배하고, 각 백엔드는 필요시 BackendSecurityPolicy를 통해 자격증명을 얻는 계층 구조다. 이를 통해 이기종 AI 백엔드들에 대한 통합 API 접근과 인증·변환 처리를 일관되게 제공한다.

# envoy-gateway-values.yaml
config:
  envoyGateway:
    gateway:                        # 이 Envoy Gateway 인스턴스가 처리할 GatewayClass를 식별하는 컨트롤러 이름. 표준 Envoy Gateway 컨트롤러 이름 그대로 사용 (커스텀 컨트롤러가 아님).
      controllerName: gateway.envoyproxy.io/gatewayclass-controller
    logging:
      level:
        default: info
    provider:
      type: Kubernetes              # Envoy Gateway가 설정을 K8s API(CRD)로부터 읽어오도록 지정 (파일 기반이 아닌 K8s-native 모드).
    extensionApis:
      # Not strictly required, but recommended for backward/future compatibility.
      enableEnvoyPatchPolicy: true  # Agent Router가 OpenAI/Bedrock 같은 AI 백엔드를 Backend CRD로 정의할 수 있게 함.
      # Required: Enable Backend API for AI service backends.
      enableBackend: true           # 필수: Backend API(CRD) 활성화. AI 서비스 백엔드(OpenAI, Bedrock 등)를 Kubernetes 리소스로 정의하기 위해 Agent Router가 사용하는 확장 API.
    # Required: AI Gateway needs to fine-tune xDS resources generated by Envoy Gateway.
    extensionManager:
      hooks:
        xdsTranslator:              # Envoy Gateway가 생성한 xDS(listener/route/cluster/secret) 설정을 Agent Router 컨트롤러에게 넘겨 후처리(Translation→Cluster→Route)하게 하는 hook. 이게 Agent Router가 Envoy 위에서 동작하는 핵심 메커니즘

            listener:
              includeAll: true      # includeAll: true로 모든 리소스를 확장 프로그램에 전달
            route:
              includeAll: true
            cluster:
              includeAll: true
            secret:
              includeAll: true
          post:                     # post 단계에서 Translation → Cluster → Route 순서로 Agent Router가 개입해 AI 라우팅/토큰 처리 등 커스텀 로직을 xDS에 주입함. Agent Router가 Envoy Gateway 위에서 동작하는 핵심 메커니즘
            - Translation
            - Cluster
            - Route
      service:
        fqdn:                       # 아직 설치 안 된 Agent Router 컨트롤러가 이 이름/네임스페이스/포트로 떠야 매칭됨. 다음 단계가 바로 이 컨트롤러 설치라는 뜻입니다
          # IMPORTANT: Update this to match your AI Gateway controller service

해설:

  • Init Container: ai-gateway-extproc (이미지: envoyproxy/ai-gateway-extproc:v1.1.0) — Init 컨테이너로 떠 있지만 실제로는 계속 살아있는 프로세스다. K8s의 native sidecar 기능(restartPolicy: Always가 암묵적으로 적용된 initContainer)을 사용해 envoy 컨테이너와 함께 상시 구동된다.
  • extProcAddr unix:///etc/ai-gateway-extproc-uds/run.sock — Unix Domain Socket으로 envoy와 통신(같은 ai-gateway-extproc-uds emptyDir 볼륨을 envoy 컨테이너와 공유)
  • configBundlePath /etc/filter-config-bundle — AIGatewayRoute/AIServiceBackend 등 CRD가 컨트롤 플레인에 의해 변환된 필터 설정을 Secret으로 마운트받음
  • endpointPrefixes openai:,cohere:/cohere,anthropic:/anthropic — 프로바이더별 API 스키마 변환 경로 매핑
  • Readiness 체크는 failureThreshold=1로 상당히 엄격 — extproc이 잠깐이라도 응답 못하면 즉시 unready 처리되어 트래픽이 안 흐르게 막음
  • 메인 컨테이너: envoy (이미지: envoyproxy/envoy:distroless-v1.38.1) — --config-yaml에 정적 부트스트랩 설정이 통째로 박혀있고, 나머지 라우팅/클러스터 설정은 xDS(ADS, DELTA_GRPC)로 envoy-gateway.envoy-gateway-system.svc.cluster.local:18000에서 실시간 수신한다. 주목할 클러스터: xds_cluster(Envoy Gateway 컨트롤 플레인과의 mTLS 연결), default/envoy-ai-gateway-basic(실제 백엔드로 가는 EDS 기반 클러스터, least_request 로드밸런싱 사용). 포트 19001(metrics)/19003(readiness)만 노출 — 실제 사용자 트래픽 리스너는 xDS로 동적 주입되는 구조(LDS/CDS via ADS).
  • 부가 컨테이너: shutdown-manager — Envoy Gateway가 제공하는 graceful shutdown 헬퍼. Pod 종료 시 새 연결을 거부하고 기존 연결을 다 처리할 때까지 기다린다.

28. Gateway API Inference Extension 소개

참고 자료: gateway-api-inference-extension.sigs.k8s.io, Github

Agent Router가 지능형 라우팅 및 로드 밸런싱을 사용해 추론 요청을 효율적으로 전달하는 기능이다 - Docs

💡
비유로 이해하기: Gateway API Inference Extension은 "종합병원의 접수/배정 시스템"과 같다. 일반 API Gateway가 "어느 창구가 비었는지" 정도만 보고 배정한다면(연결 단위 로드밸런싱), Inference Extension은 "이 환자는 어떤 전문의(모델)가 필요한지, 그 전문의의 대기줄이 얼마나 긴지, 이미 진료 기록(캐시)이 있는 병원인지"까지 보고 최적의 곳으로 배정한다.

핵심 구성요소:

  • Endpoint Picker(EPP) — "Inference Router"의 구현체로서, 요청을 어느 엔드포인트로 보낼지 결정하는 핵심 컴포넌트다. Gateway가 요청을 특정 InferencePool로 보내야 한다고 판단하면 요청 정보를 EPP로 전달하고, EPP는 InferencePool 엔드포인트들로부터 메트릭(Prefix Cache 상태, LoRA Adapter 가용성 등)을 수집해 최적의(비용 대비 성능이 좋은) 엔드포인트를 선택한다. 이 저장소가 제공하는 EPP는 컨포먼스 테스트용 경량 참조 구현(lwepp)이며, 실제로는 llm-d-router 같은 별도 구현체를 쓰는 것이 권장된다.
  • Body Based Router(BBR) — OpenAI 스타일 API 요청의 본문(body)에서 모델명을 추출해 X-Gateway-Model-Name(또는 유사한) 헤더로 주입하는 외부 gRPC 서비스다. Envoy는 헤더만 보고 라우팅할 수 있기 때문에, body 안에 있는 모델명을 헤더로 끌어올려주는 역할을 한다. ext_proc의 확장 형태로 동작한다.

참고 자료: Gateway API Inference Extension GitHub에는 "EPP와 관련 API, BBR 패키지는 llm-d/llm-d-router, llm-d/llm-d-inference-payload-processor 저장소로 이전되었으며, 이 저장소에는 더 이상 새 코드를 받지 않고 곧 archive될 예정"이라는 중요한 공지가 올라와 있다. 즉, 이 실습 시점 이후 EPP/BBR 구현체의 공식 위치가 바뀔 수 있다.

29. HTTPRoute + InferencePool 실습 (GPU 없이 CPU만으로 가능!)

참고 자료: HTTPRoute + InferencePool 공식 문서

표준 Gateway API HTTPRoute와 직접 통합하는 단순 추론 라우팅 시나리오다.

Request Processing Flow:

  1. Client Request: 클라이언트가 추론 요청을 Gateway로 전송
  2. Route Matching: HTTPRoute가 경로 접두사로 요청을 매칭
  3. InferencePool Resolution: Envoy Gateway가 InferencePool 백엔드 참조를 해석
  4. Endpoint Selection: Endpoint Picker Provider(EPP)가 최적 엔드포인트를 선택
  5. Request Forwarding: 선택된 추론 백엔드로 요청 전달
  6. Response Return: 클라이언트로 응답 반환

가장 기본이 되는 xDS 여섯 개 API — LDS(Listener Discovery Service), RDS(Route Discovery Service), CDS(Cluster Discovery Service), EDS(Endpoint Discovery Service), SDS(Secret Discovery Service), ADS(Aggregated Discovery Service) — 에 대한 설명은 Envoy 공식 xDS Protocol 문서와 대조해보면 정확히 일치한다. 다만 공식 문서에는 RTDS(Runtime Discovery Service)라는 API도 나오는데, 본문은 이를 다루지 않는다. 이는 원문이 처음부터 LDS/RDS/CDS/EDS/SDS/ADS 여섯 개만 범위로 잡았기 때문이라, 문제 될 만한 누락은 아니다.

Envoy Agent Router의 v0.1 → v1.0 capability 비교표도 Announcing Envoy AI Gateway 1.0 블로그와 나란히 놓고 보면 숫자 하나까지 그대로 맞아떨어진다. AI 프로바이더 수가 2개(OpenAI, AWS Bedrock)에서 16개로 늘며 cross-provider 변환이 추가된 것, API 서페이스가 Chat completions 하나뿐이던 데서 completions·embeddings·image generation·audio·Responses API까지 넓어진 것, 아예 없던 MCP gateway가 서버 멀티플렉싱·툴 라우팅·세밀한 인가를 갖춘 풀스펙으로 자리 잡은 것, Multi-tenancy & routing이 토큰 레이트리밋 하나에서 호스트네임 기반 라우팅·모델 가상화·쿼터 기반 레이트리밋으로 확장된 것, Control-plane API가 실험 단계였던 v1alpha1에서 안정 버전 v1beta1로 올라간 것 — 모두 원문 표와 정확히 일치한다. 참고로 이 v1.0은 블로그 게시일 기준 2026년 6월 23일에 출시됐다.

버전 번호들 — Envoy Gateway v1.8.1, Agent Router의 ai-gateway-crds-helm/ai-gateway-helm v1.1.0, MetalLB v0.16.1 — 도 각 프로젝트의 GitHub Releases와 공식 릴리스 노트에서 실제로 존재하는 릴리스로 확인된다. Envoy Gateway v1.8.1은 내부적으로 Envoy 1.38.1을 사용하고, ai-gateway v1.1.0은 "안정화된 1.x API 위에서 나온 첫 마이너 릴리스"로 소개돼 있다. 다만 이런 버전 값은 각 프로젝트가 새 릴리스를 낼 때마다 바뀌는 값이라, 독자가 실습하는 시점에는 더 최신 버전이 나와 있을 가능성이 높다.

kubectl/helm 명령의 옵션과 순서는 원문을 그대로 옮겨 실었고 임의로 손대지 않았다. 예외가 하나 있는데, 30.1절의 qwen25-05b-inferencepool.yaml은 원문 자체에서 일부 줄(livenessProbe, readinessProbe, volumes 필드)이 편집 과정에서 잘려 있었다. 이 문서에서는 구조가 동일한 llama32-1b용 YAML(29.1절)을 참고해 그 부분을 정상적인 형태로 복원했다 — 원문의 오타·잘림이며 Agent Router 자체 스펙의 문제는 아니다. original_destination_cluster(ORIGINAL_DST 타입)나 x-ai-eg-model 헤더 기반 라우팅 같은 Envoy 설정 개념들도, 소스 문서가 인용한 llm-d의 실제 envoy.yaml과 이 문서 24.2절·26절·30.2절의 실습 결과로 다시 한번 확인됐다.

정정이 필요한 부분은 하나 있다. AAIF(Agentic AI Foundation) 출범 배경과 Envoy AI Gateway → Agent Router 이름 변경 시점에 관한 서술인데, 이름 변경 시점 자체 — 2026년 9월 10일, AAIF에 Agent Router라는 이름으로 합류 — 는 theagentrouter.ai 블로그의 "On 10 September, Envoy AI Gateway officially joins the Agentic AI Foundation as Agent Router"라는 문장으로 정확히 확인된다. 문제는 원문(Notion 소스)에 있던 "Envoy AI Gateway 프로젝트가 2025년 8월 25일에 Linux Foundation에 벤더 중립 거버넌스로 기증됨"이라는 서술이다. 이는 사실이 아니다. 그날 Linux Foundation에 기증된 프로젝트는 Envoy AI Gateway가 아니라 Solo.io가 만든 별개 프로젝트인 "agentgateway"다 — Linux Foundation 공식 보도자료와 AAIF 블로그 모두 주어를 "agentgateway"로 명시하고 있다. agentgateway도 이후 AAIF에 합류하긴 했지만 Envoy AI Gateway/Agent Router와는 완전히 다른 프로젝트다. 이름이 서로 비슷해서(agentgateway ↔ Agent Router) 혼동하기 쉬운데, 전자는 Solo.io가 만든 별도의 AI 네이티브 프록시이고 후자는 이 문서가 다루는 바로 그 Envoy AI Gateway의 새 이름이다. Envoy AI Gateway/Agent Router 자체가 정확히 언제 Linux Foundation에 기증됐는지에 대한 명시적 날짜는 이번에도 확인하지 못했다 — 확실하게 확인할 수 있었던 것은 "9월 10일 AAIF 합류" 뿐이다.

마지막으로, 실습 중 독자마다 값이 달라지는 항목들도 빠짐없이 짚었는지 다시 점검했다. OpenAI API 키(<YOUR_OPENAI_API_KEY>, 20·27절), kind extraMounts용 로컬 경로(<YOUR_LOCAL_PATH>, 11.1절), MetalLB IP 풀 대역(<YOUR_IP_POOL_RANGE>, 23.1절), Admin API 접속용 호스트 IP(<YOUR_HOST_IP>, 25.3·27.2절)는 모두 placeholder로 표시해뒀다. kind 클러스터의 Docker 네트워크 대역(172.18.0.0/16)이나 Gateway External IP(172.18.255.200 등)는 원문에 구체적인 예시값으로 나오지만, kind가 그때그때 자동으로 할당하는 값이라 실습 환경마다 달라질 수 있다는 점을 각 절에서 짚어뒀다. AWS Bedrock 연동에 필요한 AWS 계정 관련 값은 원문에서도 링크만 언급되고 실제로 실습되지는 않았기 때문에(Part B 20절 말미), 이 문서에서도 마찬가지로 참고 링크만 남겨두었다.
